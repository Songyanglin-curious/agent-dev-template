# 核心准则

本目录保存写代码时必须遵守的设计规则。每条规则有一个稳定编号，并在任何领域都成立：如果一条规则只在某个业务场景成立，它属于模块文档或子系统页，不属于这里。

## 与相邻层级的分界

- **defensive-patterns**：修改某类工件前要核对的缺陷模式，回答“怎样避免写错”。
- **core-guidelines**：设计、编写和自我审查时的规则，回答“怎样才能写好”。
- **subsystems / 模块文档**：具体能力的类型、语义和契约，回答“这个系统是什么样”。
- **Agent Note**：规则形成时的取舍与理由，回答“为什么这样规定”。

规则本身不重复理由的长篇论证；它用一行理由说明代价，需要完整背景时链接 Agent Note。

## 规则格式

每条规则使用 [`G.1`](general.md#g1-规则格式) 定义的结构：`要求`、`理由`、`判据`、`边界`。编号由领域前缀和序号组成，例如 `S.1`、`D.2`，发布后不复用、不重排；删除规则时保留编号空缺，避免外部引用指向不同含义。

## 维护

新增规则的前提是同一正确或错误写法在评审中反复出现，并且规则在另一个功能上仍然适用。修改规则编号、含义或边界时，同步检查引用它的文档与脚本。
