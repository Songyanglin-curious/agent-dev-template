# 新增文档门禁

## 适用场景

一条已记录的规则能由文件内容、路径或 Git 状态机械判定，而且现有门禁还未覆盖。文档是否属实、职责划分是否合理等语义问题留给评审。

## 前置条件

找到规则的唯一归属及一个能明确判错的反例。按[工具模块](../../scripts/README.md)准备运行环境；使用与待检查文件同根的项目工具。涉及 Git 的检查还需该工作树自己的可解析基线。

## 步骤

1. 在[文档门禁](../subsystems/documentation-gates.md)说明检查对象、实际扫描范围和失败条件。先确认输入由文件发现规则还是显式清单决定。
2. 在 [scripts](../../scripts/) 实现检查，复用现有的文件发现与解析，不另写遍历或 Markdown 解析器。用清单登记路径时同时校验缺失文件和过期条目。
3. 通过时报告实际检查数量；违规时输出文件、可得的行号和期望值，以非零退出。见[脚本准则](../core-guidelines/scripts.md)。
4. 在[命令清单](../../package.json)注册单项入口，并加入适用的 `test:docs` 或 `test:notes`。项目需要按此改动提醒同步文档时，再登记[路径映射](../../scripts/change-doc-rules.json)，不要假定已有规则覆盖。
5. 为门禁自测增加独立的最小反例，明确断言退出码与诊断；同时保留能通过的输入。同步受影响的[工具说明](../../scripts/README.md)。

## 验证

先单独运行新注册的检查，再运行 `pnpm run test:gates` 及它所属的总入口。确认反例被拒绝、合规输入通过、摘要的数量与实际输入一致。项目尚无该类文件时，零是合理结果，但不能据此宣称反例也会被拒绝。

## 失败恢复

- 检查数意外为零：核对根目录、匹配路径和排除条件，不放宽规则来掩盖漏检。
- 反例未被拒绝：先验证测试是否经过真实检查入口、违规文件是否进入扫描范围，再查条件与退出码。
- 清单条目失效：恢复目标，或删除不再适用的条目并说明理由；同一违规重复报告时合并检查归属。
