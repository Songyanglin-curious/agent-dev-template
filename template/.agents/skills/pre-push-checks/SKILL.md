# 提交或推送前的本地检查

## 先确定要检查哪些改动

1. 在已接入项目内，用 `git rev-parse --show-toplevel` 核对项目自己的 Git 根，用 `git status --short --branch` 区分分支和用户工作。不要将上层仓库当作目标仓库，不为执行检查擅自初始化或提交。
2. 选择可解析的基线：已有 upstream 时用实际跟踪引用；本地分支或首次推送时用明确选择的本地 ref。仅检查工作区可以用 `HEAD`，但它不覆盖已经提交的分支差异。基线不存在时报告缺口，不猜测远端或默认分支。
3. 运行 `pnpm run change-scope --base <ref>`（替换为上一步核实的引用）。它列出已提交、已暂存、未暂存、未跟踪的路径，不判断应跑哪些检查。打开改动所属的规则后，再决定取证范围。

## 按触及面选择证据

| 实际变更 | 优先检查 |
|---|---|
| 文档、链接、元数据、预算、模块与子系统关联 | `pnpm run test:docs` |
| Note 分类、格式或归档 | `pnpm run test:notes` |
| 研发任务状态、路径或链接 | `pnpm run verify-tasks` |
| 门禁逻辑或共享解析 | 相应单项门禁与 `pnpm run test:gates`，确认违反规则时确实失败 |
| 变更范围工具 | `pnpm run test:tools` |
| 目标项目行为、持久化、构建或可见输出 | 目标项目已具备、能使该回归失败的聚焦测试或人工核验；不假定通用模板提供业务测试 |

模板没有 CI 或 Git hooks。以上命令由执行者在本地项目根主动运行；检查结果未受后续改动影响时不必重复。若没有独立 Git 仓库或已提交的基线，注明依赖 Git 的检查未完成，不借用上层仓库或设置例外制造通过结果。

## Git 操作与失败处理

- 分别审阅已暂存、未暂存和新增文件；不要混入无关内容、凭据或用户的改动。校验绿灯不代表获准提交或推送。
- 获准推送时先核实实际 remote、分支与 upstream；首次推送不假定远端同名分支存在。推送后按实际目的引用核对提交。无远端或未推送时只报告本地状态。
- 历史重写另需明确授权；确需更新远端历史时用带 lease 的保护，不强制覆盖未知更新。发布、部署、数据迁移仍需单独授权。
- 检查失败即停，保留具体命令、失败原因与影响。凭据、权限、网络或工具不足时报告受阻项，不跳过必要检查或修改测试来掩盖失败。交付时区分通过、失败和未运行。

[代码审查](../code-review/SKILL.md)负责语义判断；[文档门禁](../../../docs/subsystems/documentation-gates.md)说明机械检查的覆盖边界。
