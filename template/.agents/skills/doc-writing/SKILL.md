# 项目文档编写

读者应该能从入口页找到需要的模块，按文档完成一次操作，认出成功或失败，并找到负责该行为的代码。文档整理不是架构接入授权；模块和子系统边界不清时，先按 [project-onboarding](../project-onboarding/SKILL.md) 提出有证据的候选项。

## 写之前：确定归属

1. 读适用的 `AGENTS.md`、[文档标准](../../../docs/AGENTS.md)、目标页、入站索引及所属代码和测试。明确读者从哪里开始、要完成什么、失败后能做什么。
2. 模块事实随模块代码维护，系统关系进架构，跨模块类型和生命周期进子系统，长期取舍进 Agent Note。当前文档描述当前行为；原始材料、讨论和决策历史不要改写成已实现的能力。
3. 按主用途选择教程或参考。教程按前置条件逐步引入概念；参考按读者查找的问题组织。在介绍内部设计之前先写最短可用路径和失败边界，穷举字段只链接到权威定义。

## 文档类型与模板

先打开对应模板。`kind` 与模板一一对应；普通索引和临时交接页不冒充模块文档。

| kind | 使用时机 | 模板 |
|---|---|---|
| `module` | 一个有独立职责的软件单元需要说明能力、用法、契约和限制 | [模块](templates/module.md) |
| `module-group` | 一组直接成员需要联合导航，成员间的分工与组合会影响选择 | [模块组](templates/module-group.md) |
| `persistence-change` | 确认检测到的持久化结构变化，记录前驱、变后结构和兼容性判断 | [结构变更](templates/persistence-change.md) |
| `persistence-release` | 按实际发布标签回溯结构差异，不做兼容性确认 | [发布观察](templates/persistence-release.md) |
| `persistence-format` | 固定选定历史版本的来源及完整 schema，不作为当前写入规范 | [历史格式](templates/persistence-format.md) |

三种持久化模板约定记录格式，不提供业务数据提取器。只有目标项目可以从其实际数据格式产生并验证结构证据时，才建相应记录；临时取舍进 Agent Note，不伪造摘要、标签或兼容结论。新增 kind 前要同时具备独立模板、归属位置和能识别它的校验。

## 事实核验与交付

- 根据 manifest、入口和调用方核实模块形态。有安装机制才写安装步骤；没有安装机制的模块只写可复现的调用或加载方式。组文档每个成员都链接到实际的直接下属文档。
- 对照当前源码、配置与测试核实字段、默认值和限制。在安全且获授权的环境按展示的形式验证操作，记录可观察结果。需要凭据、网络或写操作却无法验证时，区分证据和待核验项，不用旧文档代作证明。
- 改动从事实的归属方开始，同步修复入站链接、导航、生成区域和衍生产物；不手改生成区域。移动页面后同时核对路径和标题锚点。
- 在项目根运行 `pnpm run test:docs`。本地门禁检查文档结构，不证明产品行为；交付时分别列出已验证的结构、实际复现的操作以及缺口。
