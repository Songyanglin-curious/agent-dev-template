# 代码审查

**这是判断指南，不是逐项打勾的完整清单。**

## 建立范围与依据

1. 确认目标项目自己的 Git 根、分支和用户改动；不要借用上层仓库作为基线，不要覆盖未提交内容。
2. 验证评审基线，运行：

```sh
pnpm run change-scope --base <verified-base>
```

`change-scope` 只报告路径，不判断检查或文档归属。

3. 读本次任务、原始输入、相关 Agent Note 和根 [AGENTS.md](../../../AGENTS.md)。
4. 按改动路径打开归属要求： [docs/AGENTS.md](../../../docs/AGENTS.md)、[architecture](../../../docs/architecture.md)、[subsystems](../../../docs/subsystems/README.md)、模块 README、[core-guidelines](../../../docs/core-guidelines/README.md)、[defensive-patterns](../../../docs/defensive-patterns/README.md) 和测试策略。
5. **先读要求，再读 diff。** 不要凭记忆对照规则，也不要用规则名称代替证据。

## 读 diff

- 读完整 diff 和足够的周边代码、测试、配置，不只看 hunk。
- 追踪变更接口的两侧：生产者、消费者、错误、取消、所有权和清理。
- 检查真实入口路径：测试是否经过实际启动/加载/调用路径，而不是手工挂载的替身。
- 检查测试是否会在预期回归上失败；负向用例是否通过真实 runner 失败。
- 检查文档是否随行为、契约、默认值或限制同步。
- 发现实现与任务、Agent Note 或 PR 描述不一致时，先确认哪一个是当前事实。

## 审查面

按 diff 触及的面选择，不要求每次全部执行。

| 面 | 看什么 |
|---|---|
| 行为与契约 | 调用方能否依赖声明的行为；错误、取消、时序、空值和边界是否一致 |
| 范围与必要性 | 新字段、适配器、状态机、选项和兼容路径是否服务于当前要求；是否混入无关功能 |
| 所有权与生命周期 | 谁创建、谁释放、谁在重入或并发时仍可使用；清理是否早于消费者结束 |
| 数据与持久化 | 结构变化是否有兼容决策、迁移、回滚和记录；旧数据是否仍可读 |
| 安全 | 认证、授权、凭据、路径、注入、沙箱和外部输入边界 |
| 测试 | 是否验证行为而不是复述实现；是否覆盖失败、并发、清理和真实入口 |
| 文档 | 当前事实是否更新；理由是否只留在 Agent Note；是否出现重复或过期描述 |
| 依赖与构建 | 新依赖是否有净收益；manifest、锁文件、构建面和发布路径是否同步 |
| UI/CLI/输出 | 用户或模型可见输出是否按预期变化；是否需要快照或实际检查 |

## 报告

- 每条 finding 写清：缺陷、位置、影响、证据。
- 局部缺陷放在最紧的 diff 范围；跨切面问题放在总结或任务交付说明。
- 区分 blocker 和 suggestion；不要用 nit 淹没 blocker。
- 已被绿色门禁覆盖的问题不重复报告；门禁不能证明的语义问题才需要评审。
- 对作者或评审意见逐条验证：接受则修，拒绝则给出技术理由，不做表演式同意。

## 边界

- 小改动不需要完整审计；按风险选择审查面。
- 不以“清单未全部打勾”作为拒绝理由；以契约破坏、行为错误或证据缺口作为理由。
- 测试通过不等于设计正确；覆盖率不等于场景正确。
- UI 的视觉接受、设计取舍和发布授权仍由对应角色决定，不由本 Skill 代替。
