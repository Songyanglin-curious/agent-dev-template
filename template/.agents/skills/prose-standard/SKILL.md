# 文字标准

## 范围和权限

要求明确到文件、目录或某处输出；未给范围时先说明缺什么，不推断全库。评审只报告，获准编辑才改。默认自行处理明确改法，仅在用户要求校准时就确有取舍的写法提问。排除第三方文件、冻结的归档 Note 和生成产物；生成文字发生变化时应修改生产方，然后重新生成并核对消费方。

## 保留完整命题

先找出谁在什么条件下必须、可以或不能做什么，再决定删改。时序、执行者、归属、例外、否定性保证、失败、副作用和结果都要保留。把模糊术语换成具体字段、动作或不变量；如果它准确指向一项技术约定，就保留术语本身。不为字数目标减弱义务，也不把期望或假设改成既有事实。

使用处要能看懂其契约；长篇理由、算法和历史可链接归属方。能从代码直接看出的过程不用再写。若没有解释会诱使维护者做出错误简化，应留下那个非显而易见的理由，而非说服评审者的过程。

## 不同位置需要保留什么

| 位置 | 应能回答的问题 |
|---|---|
| 公共接口与模块文档 | 输入和返回有哪些有意义的区别？失败、取消、副作用、所有权、持久性和限制如何影响调用方？ |
| 内部注释与测试 | 哪个不变量或竞态解释了实现？为什么必须走某个真实入口或间接观察？删除代码复述和测试走查，不删抑制告警的必要理由。 |
| 操作指南与诊断 | 执行者具备什么前提，沿哪个入口操作，如何识别成功、失败及恢复？诊断指明出错对象和违反的规则。 |
| 用户可见文字 | 实际行为、标签、辅助名称和格式是否一致？哪些测试锁定了措辞？没有授权或场景验证时不要顺手改输出。 |
| Note 与复盘 | 哪些理由、备选、证据和验证缺口影响后续决策？哪些事件能确立因果？这些内容不要因精简而丢失。 |
| Skill 与规则 | 谁在什么条件下使用？作用范围、禁止行为、例外和退出条件是什么？判断指南不是机械清单。 |

## 交付

对照[文档标准](../../../docs/AGENTS.md)及所属实现逐项判断保留、补充、删减或延期；不能确定原义时不改写。页面结构和预算见 [doc-writing](../doc-writing/SKILL.md)，脱离会话后无法解析的文字见 [trim-cot-leakage](../trim-cot-leakage/SKILL.md)。编辑后运行相关文档或行为检查，报告实际改动、刻意保留的契约与未核验项。
