# 系统认知的组织

简单来说这就是对于 系统 更深一步不同的描述
简单的来说 dsh分了三层

架构  强调整体理解
子系统 强调精确认识
模块 强调技术细节

## 架构

### 静态组成

在架构详细描述架构**静态组成**  比如

整个系统基于什么机制构建？
系统如何被组装和启动？
各核心模块分别承担什么职责？
等等架构方面的内容

介绍的是各模块在系统中的位置和职责，并链接到进一步的技术资料。

### 表达动态行为

轮次流程 等

## 子系统

这一级关注的不再是整个系统如何组成，而是：某个子系统提供了哪些能力，这些能力具有怎样的精确语义和技术契约。

## 模块

这一级关注的不再是整个系统如何组成，而是：某个子系统提供了哪些能力，这些能力具有怎样的精确语义和技术契约。

## **一、DSH 如何约束文档结构？**

| 约束机制       | 实际作用                       |
| -------------- | ------------------------------ |
| 系统架构       | 决定系统的主要组成及职责       |
| 软件包划分     | 决定模块的实际边界             |
| 文档治理规范   | 决定各层文档的描述范围         |
| 文档编写 Skill | 约束创建、修改和重组方式       |
| Code Review    | 审查研发变更及相关文档         |
| 工程检查       | 验证部分结构、格式及一致性要求 |

DSH 明确规定，文档主题及其所在层级决定描述范围，子系统中的类型由声明该类型的软件包所属分组负责记录。新增软件包也有对应的 README 创建规范。

GitHub+2

因此，文档结构并不是 AI 临时归纳出来的一套知识分类，而是建立在已经存在的工程结构之上。
