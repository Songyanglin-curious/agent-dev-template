## Module 与 Module Group 的定义

DSH 以 Package 作为代码文档的基本组织单元。Package 具有明确的工程边界，可以通过包清单、公开入口和依赖关系进行识别。

agent-dev-template 面向不同语言、技术栈和项目结构，因此采用更通用的 Module 概念，而不绑定特定的包管理机制。

### Module

Module（模块）是项目中具有明确职责、相对稳定的边界和交互契约，值得被独立理解与维护的软件单元。

模块的划分由项目实际架构决定，而不是由文件夹层级决定。不同技术体系下的 Package、Project、Library、Service 或具有明确边界的业务组件，都可以成为 Module。

Module README 随对应模块维护，主要描述：

* 模块的定位、职责及能力。
* 模块的使用方式与交互契约。
* 可观察行为、失败情形及限制。
* 内部设计、数据及生命周期。
* 依赖关系与源码导航。

不是所有代码目录都是 Module，也不是所有 Module 都必须建立独立的 README。是否建立文档取决于其独立认知和维护价值。

### Module Group

Module Group（模块组）是对多个相关模块的组织，用于说明一组模块的整体能力、职责分工和组合关系。

Module Group README 主要描述：

* 模块组的定位及整体能力。
* 直接下属模块或模块组的职责。
* 模块之间的关系及组合方式。
* 指向各模块详细文档的导航。

Module Group 不重复描述具体模块负责的事实，也不要求自身具有独立的软件入口或交互契约。

仅在项目实际存在模块分组且具有独立说明价值时建立 Module Group README，不强制每个父级目录建立索引文档。

### 与其他系统文档的关系

| 文档           | 主要职责                                 |
| -------------- | ---------------------------------------- |
| Architecture   | 系统全貌、总体结构及主要组成部分的关系   |
| Subsystem      | 系统特定能力、行为、职责边界及跨模块协作 |
| Module Group   | 相关代码模块的组织、职责分工及导航       |
| Module         | 具体软件单元的能力、契约及内部设计       |
| Source / Tests | 精确的实现事实与验证证据                 |

上述关系是系统认知的组织方式，而不是固定的目录层级。Subsystem、Module Group 与 Module 不要求一一对应，也不要求所有项目具备全部层级。

### 文档类型与校验

保留两种独立的文档类型及对应模板：

* `module` → `templates/module.md`
* `module-group` → `templates/module-group.md`

文档类型应根据实际职责和内容确定，而不是简单根据目录名称或深度推导。

模块识别、文档覆盖范围及自动化校验方式由具体项目结合实际工程结构确定，暂不建立跨技术栈的统一识别规则。
