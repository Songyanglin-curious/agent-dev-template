## 1. 整体结论

**当前项目是一个可以运行的“文档治理原型”，还不是成熟的通用模板。**

它已经具备：

- 清晰的四层归属原则；
- 根 `AGENTS.md` 的常驻规则和触发表；
- 一个完整的 `dev-workflow` 流程说明；
- 文档标准、模块/子系统模板和 15 个 `verify-*` 门禁；
- 7 个真实执行的门禁失败路径测试；
- 一个 GitHub Actions 工作流；
- 2 条格式合法的 implemented Agent Note。

它还没有具备：

- 可交付的 `template/`；
- 真实软件模块、模块组和子系统语料；
- 强制的文档同步；
- 提案与实施授权的实际关卡；
- 对多数门禁的失败路径验证；
- 持久化记录、归档记录、复盘记录的实际实例；
- 可确认的 CI 必需检查/分支保护。

### 成熟度判断

| 维度             | 判断       | 依据                                                                         |
| ---------------- | ---------- | ---------------------------------------------------------------------------- |
| 原则与归属设计   | 较成熟     | 四层结构、一个事实一个归属、层级边界写得清楚                                 |
| 文档结构门禁     | 中等偏成熟 | 链接、换行、预算、Note 格式等有真实脚本和部分失败测试                        |

## 3. 研发活动流程

### 3.1 规范写的流程

`dev-workflow` 把一次非机械性研发定为 8 步：

1. 明确问题与验收；
2. 按架构 → 子系统 → 模块定位影响面；
3. 判断是否建立提案（长期取舍、被否决方案、跨模块契约、不可逆/持久化/安全）；
4. 实施代码、测试、配置和文档；
5. 运行 `verify-change-docs`，按触发表核对归属文档；
6. 沉淀可复用的工程知识；
7. 运行 `test:gates`、`test:docs`、`test:notes`；
8. 交付报告。

这套流程本身是清楚的，问题在于**每一步的实际约束强度不同**。

### 3.2 实际发生的流程

| 环节 | 规范期望                                              | 实际发生                                                                   | 约束                                    |
| ---- | ----------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------- |
| 输入 | 原始需求进 `研发输入/`                              | 有 DSH 梳理、术语表、流程草稿和未跟踪报告                                  | 无门禁，符合设计                        |
| 启动 | 根 `AGENTS.md` 要求先加载 `dev-workflow`          | 取决于 Agent 是否遵守；没有运行时证据                                      | 纯规则                                  |
| 定位 | 读架构、子系统、模块                                  | 只有文档体系自身可读；没有真实产品模块                                     | 无门禁                                  |
| 决策 | 长期取舍进 `proposed/`，已做决策进 `implemented/` | 2 条 Note 全部在最后一次提交直接以 `implemented` 创建；0 条 `proposed` | 只有格式/分类门禁，没有“必须提案”门禁 |
| 实施 | 代码、测试、配置、文档同变更                          | 当前只有文档和门禁脚本，没有应用代码/测试                                  | 没有代码构建或代码测试                  |
| 同步 | `verify-change-docs` 输出归属方，按清单核对         | 3 条规则全部 `remind`；`--strict` 明确输出“no effect”                | **不阻断**                        |
| 沉淀 | 复盘、防御模式、准则、cookbook、Skill                 | 4 条准则、6 条防御模式、1 篇 cookbook、0 篇复盘                            | 评审承担，无门禁                        |
| 验证 | `test:gates`、`test:docs`、`test:notes`         | 本次全部通过；但主要验证结构，不验证流程                                   | 结构门禁阻断，流程不阻断                |
| 交付 | 报告列出文档影响、命令和未覆盖项                      | 没有自动检查报告内容                                                       | 纯人工                                  |

### 3.3 关键断点

这条流程最关键的断点有三个：

1. **第 3 步“是否建立提案”没有执行证据。** 项目自己的两条重大决策都没有走 `proposed/`，所以这套机制还没有被自己的研发活动验证过。
2. **第 5 步“同步文档”没有强制力。** `verify-change-docs` 是提醒器，不是门禁；CI 的 `--strict` 因为没有 `require` 规则而没有实际效果。
3. **第 7 步“验证”只覆盖结构。** 文档链接、换行、预算、Note 格式会失败；文档是否真的同步、示例是否可执行、子系统页是否随类型变化更新，都不会失败。

## 6. 与 DSH 的映射

| 层次                     | DSH                                                                     | agent-dev-template 当前                                                                                          | 判断                                                                                |
| ------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 原则                     | architecture、core-guidelines、Agent Notes rationale                    | 四层结构、一个事实一个归属、准则/模式/复盘分层                                                                   | 概念对应最强；但只有文档体系自身作为实践对象，缺少真实项目语料                      |
| 规则（AGENTS.md）        | 192 行常驻规则 + 大量具体工程约定                                       | 54 行常驻规则 + 研发活动触发表                                                                                   | 结构归属规则较清晰；具体工程约束少，因为模板不绑定技术栈                            |
| 程序（Skills）           | 22 个专项 Skill：pre-push、code review、PR 描述、归档、UI、测试可靠性等 | 5 个 Skill：`dev-workflow`、`doc-writing`、`prose-standard`、`trim-cot-leakage`、`archive-agent-notes` | 有核心骨架，但覆盖面远小于 DSH；缺少代码评审、推送前检查、PR 描述、测试可靠性等程序 |
| 校验（Scripts/Tests/CI） | `run-gates`、大规模 CI、快照/覆盖率、加权审批、Issue policy           | 15 个文档门禁、7 个失败路径测试、1 个 CI 工作流                                                                  | 文档结构检查有实际约束力；流程约束和人工审批远未达到 DSH                            |

### 6.1 已有实际工程约束力的部分

- 文档链接、锚点、段落换行、字数预算、Agent Note 格式/分类：脚本会以非零退出。
- `test:gates` 的 7 个用例：确实在临时工作区构造违规并断言失败。
- `test:docs` / `test:notes`：在当前语料上真实执行并通过。
- CI 工作流：存在，且运行同样的三个入口；但“是否必需”未知。

### 6.2 形式相似但没有同等约束力的部分

- **`dev-workflow` 的提案步骤**：DSH 的 `proposed/` 同样是可选记录，但 DSH 至少有若干真实提案案例；这里有 0 条 proposed，流程从未被验证。
- **`verify-change-docs`**：形式上是“变更影响清单”，但全部 `remind`，`--strict` 无效果，和 DSH 的 PR 审批/CI 强制不在一个约束级别。
- **“示例必须可执行”**：DSH 有 `doc-typecheck` 等机制；这里只有文字规则。
- **“subsystem 页随类型更新”**：DSH 有类型等价/子系统页检查的更强机制；这里只检查模块文档是否链接了子系统页，不检查类型变化。
- **“修改门禁必须补失败路径用例”**：DSH 有测试和 CI 覆盖门禁本身；这里没有检查“新门禁是否有测试”的元门禁。

### 6.3 有意的不同设计

这些不是缺陷，而是当前模板的边界：

- 不做双语文档配对；
- 不做文档网站；
- 不做 TypeScript 类型与源码等价检查；
- 不做具体技术栈的构建、测试、发布检查；
- 不内建 Issue/PR 生命周期自动化；
- Agent Note 采用单语，而不是 DSH 的英中配对；
- 用一个 `dev-workflow` 统一流程，而不是 DSH 的大量专项 Skill。

这些差异在 `docs/architecture.md` 的“边界”和 README 的“已知限制”中有说明，方向是合理的：模板不应绑定某一种技术栈。

### 6.4 尚未达到 DSH 的部分

- **人工审批边界**：DSH 有 PR 加权审批、Issue policy、UI 设计师/产品评审；这里没有对应的通用机制。
- **实施前批准**：DSH 的 plan mode 至少提供了一个可选的“计划批准后执行”路径；这里没有。
- **代码评审程序**：DSH 有 `dsh-code-review`；这里没有通用代码评审 Skill。
- **推送前检查选择**：DSH 有 `dsh-pre-push-checks`；这里只有全量 `test:docs`/`test:notes`。
- **PR 描述与 AI Usage**：DSH 有固定模板和分级；这里没有。
- **持久化工具链**：DSH 有提取、digest、schema 生成和 review 工具；这里只有记录格式和校验器。
- **CI 矩阵与必需检查**：DSH 有完整矩阵和分支保护；这里只有单个 docs 工作流。

## 7. 下一步建议

以下只是建议，暂不实施；按依赖顺序排列。

1. **先选一个真实试点，不要继续加机制。** 用 `scripts` 模块作为唯一模块，或引入一个小型真实模块，让模块 README、子系统关联、类型变更至少有一次真实输入。没有第二个模块，模块组/子系统/持久化门禁无法被验证。
2. **把“文档同步”二选一：要么最小强制，要么明确标为提醒。** 如果继续声称“文档跟随研发”，应给 1–2 条语义明确的 `require` 规则（例如 `scripts/**/*.ts` → `docs/subsystems/documentation-gates.md` + `scripts/README.md`）；否则应在 README 和交付报告中明确写“当前只提醒，不阻断”。
3. **补关键门禁的失败路径测试，并处理零语料。** 优先：Agent Note 分类/归档、模块 README、持久化记录、`md-wrap`、`repository-references`；同时给零语料加断言或显式警告。当前 15 个门禁只有 4 个有反向用例。
4. **用一次真实变更跑通 `dev-workflow` 的提案分支。** 选一个跨模块或不可逆的决策，实际走 `proposed/` → 评审 → `implemented/`；如果结论是“不需要 proposed”，就删除或简化该分支，避免保留一条从未使用的规则。
5. **确认 CI 是否真的阻断合并。** 如果工作流没有设为 required check，就把 CI 描述为“发现问题”，不要描述为“阻止不合规合并”；如果设为必需，记录在 README 中。
6. **最后再整理 `template/`。** 只把经过试点验证的机制放进 template，不要把当前空目录或未验证的 proposed 流程直接复制过去。

依赖关系：1 是 2/3/4 的前提；2 和 3 是 5 的前提；4 是 6 的前提。
