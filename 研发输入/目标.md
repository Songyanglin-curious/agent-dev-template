# agent-dev-template 研发体系建设背景与本次研究任务

## 一、项目目标

我希望建立一套面向 AI Agent 辅助软件研发的项目模板，主要参考 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/tree/master) 的研发文档体系。

此前尝试过 agent-docs，但实际使用中存在文档维护与研发活动脱节、AI 经常遗漏文档更新、积累的知识没有充分参与后续研发等问题。

因此，这次希望从整个软件研发过程出发重新设计，而不是单独建立一套文档管理系统。

希望体系具备以下能力：

* 帮助人和 Agent 准确理解当前系统，通过架构、子系统和模块文档建立不同层次的系统认知。
* 管理研发过程中产生的问题、方案、设计决策及其演进，保留有长期价值的设计依据和取舍。
* 让系统文档随着实际研发活动同步变化，保证文档准确性，减少过时、重复和低价值内容。
* 将研发过程中积累的工程经验转化为开发准则、防御性模式、操作指南和 Skills，使其真正参与后续研发。
* 对具有长期维护价值的持久化数据结构建立变化记录，保留历史结构、兼容性决策和验证依据。
* 通过明确的研发规则和自动化检查，减少对 Agent 自觉遵守规范的依赖。

核心原则：

让每个文档都可搜索、对新人可读，并且对 Agent 和维护者足够精确。

每个事实只保留一个归属方：源文件、测试、生成目录、模块 README、指南、Agent Notes 和草稿各自保留其自身类型的真相，其他文档通过引用建立联系，而不是重复保存相同内容。

**让 Agent 根据任务性质调用合适的工程机制，而不是让所有任务适应同一套工程流程。**

## 二、核心设计认识

我认为 DSH 效果比较好的核心原因，是它有很高比例的可执行步骤，并且有脚本配合，而不是像大多数模板一样只有一堆方向和愿望。

可以用法与律来理解：

* 法：规定方向和原则，但具体执行方式可能因人而异。
* 律：将要求转化为明确、可执行、可验证的标准。

我目前将 DSH 的机制理解为四个层次：

1. 原则：为什么要这样做。
2. 规则（AGENTS.md）：什么情况下必须做什么。
3. 程序（Skills）：具体怎么做、如何判断。
4. 校验（Scripts、Tests、CI）：如何发现没有做或做错了。

这也是 agent-dev-template 后续建设最重要的参考标准。

**以 DSH 为参照，优先复用成熟的工程机制，通过规则、Skills 和自动化检查解决大多数常见研发问题；保留必要的灵活性和人工判断，不追求穷尽所有场景，不让研发体系本身成为研发负担。**

## 三、当前项目状态

* **agent-dev-template**：我们正在研发的项目。
* **template/**：最终交付给其他软件项目使用的模板产物，目前暂时没有产出。

目前已经初步搭建了框架，包括 AGENTS.md、Architecture、Subsystems、Agent Notes、Skills、Scripts 等，但还没有进行细致打磨。

接下来希望采用自举式研发：

**让 agent-dev-template 使用自己的研发体系，来完善自己的研发体系。**

不预先设计完整体系，而是通过实际研发活动逐步验证和完善，最终将成熟且具有通用价值的机制整理到 template/。

## 四、未来模板需要解决的接入问题

除了新项目从零开始使用，还需要支持已有项目接入。

对于空项目，需要具备初始化能力，例如建立项目介绍、初始架构认知、必要的研发规则和记录。

对于已经开发了一段时间的项目，需要具备资料迁移能力。

我目前设想的方向是：

1. 对原有文档资料进行备份。
2. 将备份资料独立存放，不再要求其遵循新体系的目录、AGENTS.md、README、索引等规则。
3. 清理 AI 中间过程和低价值内容，保留有价值的当前项目文档、真实需求及外部约束。
4. 以项目代码为核心，结合保留下来的资料，重新建立系统认知、初始 Agent Notes、README 和必要的研发规则。
5. 后续研发逐步维护新体系，随着新体系接管项目，原有资料的参考价值逐渐降低，最终由项目维护者决定是否删除备份。

这是未来模板需要具备的能力，目前不要求立即实现。

## 五、本次研究任务：DSH 如何组织研发活动？

在之前 agent-dev-template 的建设过程中，我发现一个实际问题：

当我向 Agent 描述一个研发目标时，Agent 有时会直接将目标理解为实施授权，开始修改大量文件，而不是先调查现状、分析问题、形成方案供我审查。

此前 agent-dev-template 的建设过程中就出现过一次这样的情况，一次性修改了约 120 个文件，我最终不得不手动中断。

我想研究的是：

**DSH 在实际研发中，是如何处理从用户提出目标，到最终实施交付这一过程的？**

我尤其想弄清楚它究竟是直接实施，还是存在调查、方案形成、人工审查、授权实施等不同阶段。

请围绕以下问题展开研究：

### 1. 研发活动的组织方式

* 用户提出一个研发目标后，Agent 通常如何开始工作？
* 哪些情况直接进入实施？
* 哪些情况需要先调查、分析和形成方案？
* DSH 是否存在明确的提案与实施阶段划分？
* 不同研发任务是否采用不同的处理方式？

### 2. 人工参与与授权边界

* DSH 是否要求某些研发活动必须经过人工审查？
* 如果有，具体由什么机制触发？
* 人工审查发生在什么阶段？
* 用户提出目标、讨论方案和明确授权实施，在 DSH 中如何区分？
* 如果 DSH 没有强制的人工审批机制，也请明确说明，不要将推断当作实际规则。

### 3. 具体执行机制

请研究这些机制如何配合：

* 根目录 AGENTS.md 如何约束研发活动？
* Skills 如何指导调查、提案、实施和验证？
* Agent Notes 如何承载方案与决策？
* Scripts 如何参与研发流程？
* Tests 和 CI 如何保证研发结果符合要求？

重点关注它们之间的实际调用关系，而不是分别介绍每个文件的作用。

### 4. 真实研发案例

尽可能结合 DSH 已有的 Agent Notes、实际代码变更和 Git 历史，找出能够说明上述过程的真实案例。

例如：

* 一个研发需求如何形成提案？
* 提案如何被审查和调整？
* 什么时候开始实施？
* 实施完成后如何收束记录？
* 是否存在直接实施而不创建提案的情况？

需要区分 DSH 的明确规定、实际研发中观察到的行为以及基于证据的推断。
