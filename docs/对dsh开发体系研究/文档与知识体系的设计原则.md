# 文档与知识体系的设计原则

DSH 的文档体系不是一套“写文档的规范”，而是把系统认知、设计决策、工程约束和操作经验分给不同载体，并让维护动作由研发活动触发。本文整理其中可以脱离 DSH 技术栈复用的部分，以及依赖其技术栈、不宜照搬的部分。

## 按职责分层，而不是按写作体裁

DSH 先问“这个事实由谁负责”，再决定文件放在哪里；目录反映职责和生命周期，不反映体裁。按职责可以读到六类载体：

| 载体 | 拥有的事实 | 归属判断 |
|---|---|---|
| 根与子树 `AGENTS.md` | 每次会话都需要的常驻指令和导航 | 不写进常驻上下文，Agent 会漏掉吗 |
| `docs/architecture.md` | 整体组成、依赖方向、扩展点 | 这是系统的地图，还是某个部分的细节 |
| `docs/subsystems/` | 能力的概念、类型、语义、生命周期和契约 | 这是一项跨模块能力的精确契约吗 |
| 包 README | 单个软件单元的能力、使用、限制和扩展点 | 读者在选型、使用或修改这个包吗 |
| `.agents/notes/` | 一次决策的理由、放弃的方案、后果 | 代码和测试无法解释“为什么这样”吗 |
| 治理与经验 | 写作标准、结构检查、设计准则、缺陷模式、事故记录、固定步骤、Skills | 它约束开发行为、防止特定缺陷，还是保存已验证的动作 |

归属规则有三条推论，比具体目录更重要：

- 一个事实只有一个归属，其他位置只放链接；第二份副本被视为缺陷，而不是备份。
- 上层只描述下层的职责和高层行为，细节链接到负责它的页面；文档类型不会扩大描述范围。
- 知识就近保存：包的知识放在包旁边，随代码移动；集中式知识树无法承担“改这个文件要核对哪份文档”的定位。

模块与子系统的关系也刻意不一一对应。一个子系统可以跨多个包，一个包可以服务多个子系统；检查只要求包组 README 链接到真实的子系统页，或者登记豁免和理由。文档结构因此建立在实际工程组成上，而不是目录深度上。

## 让状态由结构表达

Agent Note 是 DSH 研发演进的主载体，它的设计把“记录处于什么阶段”变成路径和格式问题：

- 路径固定为 `{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`。生命周期只有 `proposed`、`implemented`、`rejected` 三种，分类是闭集，新增分类要同时改脚本和规则。
- 标题格式固定，`Status:` 的值必须与所在目录一致，正文骨架随生命周期变化；脚本交叉检查，移动目录而不改写正文会失败。
- 提案期用问题、方案、候选方案、验收条件、风险；实现后用问题、决策、候选方案、后果，并改为现在时，提案期的行动清单在交付时消失。
- 被否决的提案只在仍能阻止一个诱人错误时保留；被取代的记录可以合并删除；有历史价值但不再指导未来的记录进入冻结归档，归档后不可编辑，也不作为当前权威。
- 不建集中索引。路径就是元数据，搜索就是入口；索引只会产生第二份状态并制造合并冲突。

关键认识是：**状态是研发事实，结构是状态的表达。** 目录、状态行、章节骨架和归档冻结是同一件事的四个面，只保留文档而省略检查，状态就会退化成正文里的说法。这也解释了为什么 `proposed` 记录可以在实现开始后才创建：它记录的是“这是提案”，不是“此刻还没写代码”。

## 维护由触发条件和程序承担

文档失真的常见原因是维护动作依赖回忆。DSH 把“什么时候做什么”拆成三层：

| 层次 | 机制 | 作用 |
|---|---|---|
| 常驻规则 | 根 `AGENTS.md` 的“改动 → 必须同步”条目 | 把“记得更新文档”换成具体条件，例如修改 `agent-loop` 要更新架构页，改变已记录类型要同步子系统页，破坏性变更要写升级指南 |
| 程序 | 专项 Skill | 规定在什么场景加载哪些知识、按什么顺序判断，例如评审、推送前检查、简化调查、归档 |
| 检查 | `scripts/` 与 CI | 检查格式、链接、锚点、预算、冻结、持久化记录等可机械判定的部分 |

触发条件写得越具体，Agent 需要临场做的价值判断越少。但 DSH 的触发条件是为它自己的包、类型和发布方式写的，无法直接通用；能移植的是“把触发条件写到具体机制上”这种做法，而不是它那几十条规则。DSH 也没有为每种代码改动建立强制对应关系，其余部分仍然靠工程判断。

另一个可移植的做法是“程序按场景拆分，不建统一流程”。DSH 有二十多个专项 Skill，没有一条所有任务都必须经过的流水线；评审、推送前检查、PR 描述、简化调查各自规定判断标准，并由常驻规则在具体条目上链接。

## 机器检查划定了“可信”的边界

DSH 的门禁只覆盖可机械判定的部分：文档结构、元数据、链接与锚点、字数预算、生成区域、归档冻结、持久化记录完整性、类型与文档的一致性。语义质量、归属判断、兼容性决策和界面观感留给人工评审。

持久化文档把这个边界写得很清楚：验证无法确认记录由谁编写、是否经过人工评审。评审者要做的是对比变更前后的清单，而不是相信绿色检查。相似地，测试证明行为，不证明设计值得做；快照证明输出，不证明界面可用。

要让门禁值得信任，还需要两件事：**失败路径测试**和**语料可见性**。DSH 为部分门禁编写了失败路径测试，确认它在遇到违规时确实拒绝；如果只验证“当前语料通过”，门禁可能已经检查了零个文件。部分校验脚本在摘要里报告检查数量，例如 Agent Note 分类和链接检查，让语料缩小可见。

## 工程经验按“参与研发的方式”分层

DSH 不把所有经验写进同一类文档，而是按它在研发中的出场方式分开：

| 载体 | 内容 | 何时进入研发 |
|---|---|---|
| `core-guidelines/` | 带稳定编号的设计规则，要求在任何领域都成立 | 设计、编写、自查时 |
| `defensive-patterns/` | 按工件组织的缺陷检查：要求、缺陷、判据、边界、正反例 | 修改对应工件前查阅，评审时执行 |
| `postmortem/` | 事故经过与系统性根因，只在隐蔽、系统性、重复发现成本高时写 | 事故复盘时 |
| `cookbook/` | 已验证、会重复执行的固定步骤 | 再次执行同类任务时 |
| Skills | 场景工作流和判断标准 | 触发场景出现时加载 |
| 根 `AGENTS.md` | 把以上内容接入日常开发的入口 | 每次会话 |

分工可以概括为：文档提供认识、依据和约束，Skills 规定何时以及怎样使用这些知识，`AGENTS.md` 负责让 Agent 在合适的时机读到它们，测试和脚本检查可以客观验证的部分。知识库与 Skills 不能互相替代：只有知识，Agent 不知道何时加载；只有流程，Agent 没有判断依据。

这条链还有回环：复盘产生防御模式，反复出现的评审意见提炼成准则，反复执行的操作沉淀为 cookbook，机制缺口回到规则、Skill 或门禁。研发活动本身因此成为改进研发方式的来源。

## 不宜照搬的部分

| 做法 | 依赖 | 移植后的代价 |
|---|---|---|
| 中英文文档配对与翻译工作流 | 翻译提示词、配对记录和一致性校验 | 没有翻译需求时会变成空机制和额外门禁 |
| 文档网站与站点片段校验 | 发布站点与静态生成流程 | 模板面向不同技术栈，无法假设发布方式 |
| 文档中的类型与源码等价检查 | TypeScript 项目结构和类型系统 | 其他语言要重写整套提取器 |
| 加权审批、Issue 策略、UI 与图标评审 | GitHub 协作平台和固定评审人角色 | 本地 Git 或个人项目没有对应角色 |
| plan mode 作为执行前批准 | 产品功能，且明确不限制工具 | 不能提供“未批准不得改文件”的硬保证 |
| 大规模生成器与专用脚本体系 | 包布局、发布流程和具体语言 | 照搬会产生大量与项目无关的维护义务 |

这些做法在 DSH 中成立，是因为它的技术栈、发布方式和团队规模支持它们；换一个项目，机制的真实成本可能高于收益。判断标准不是“DSH 有没有”，而是“这条约束在这个项目里能不能被稳定执行和验证”。

## 最小可复用内核

如果只保留一套最小方案，DSH 的经验收敛为七条：

1. 每个事实一个归属，上层只写职责和链接，副本按缺陷处理。
2. 归属结构反映研发活动，不反映写作体裁；模块知识跟随代码。
3. 常驻规则只写具体触发条件，每条指向真实存在的文档、Skill 或脚本。
4. 能机械判定的约束交给脚本，并在同一变更内同步归属文档；门禁要有失败路径测试和语料计数。
5. 决策记录区分提案、已实现和被否决，状态由路径和格式表达，并保留删除与冻结的出口。
6. 经验按参与研发的方式分层，最终接到常驻入口上。
7. 语义、归属、兼容性和界面判断留给人工评审，不假装机器能判断。
