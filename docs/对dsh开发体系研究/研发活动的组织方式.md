# 研发活动的组织方式

本文回答一个具体问题：从用户提出目标到实施交付，DSH 是否划分调查、方案、人工审查和授权实施等阶段，这些阶段又由什么保证。结论来自仓库规则、提交历史和真实案例，并区分“已实现机制”“观察到的行为”和“基于证据的推断”。

## 结论

DSH 没有统一的研发流水线。它提供可选的提案文档生命周期，但没有“先批准提案才能实施”的门禁；强制执行落在三处：同一变更内的文档与记录义务、结构门禁、合并前的人工评审。实施通常先发生、评审在后，提案只在部分高风险变更中真正前置。

因此，“用户提出一个目标”在 DSH 的制度上不等于“授权实施”，但也没有机制阻止 Agent 把它当成授权。这条边界依赖 Agent 遵守文字规则，以及评审者在合并前追回。

## 判读框架：法与律

本项目用“法”和“律”区分两类要求：法规定方向和原则，执行方式可以因人而异；律把要求转成明确、可执行、可验证的标准。DSH 的效果来自律的比例高，而不是原则写得多。按这个框架，它的机制分成四层：

| 层次 | DSH 载体 | 回答的问题 |
|---|---|---|
| 原则 | `docs/architecture.md`、`docs/core-guidelines/`、Agent Note 中的理由 | 为什么这样设计 |
| 规则 | 根 `AGENTS.md` 与各子树 `AGENTS.md` | 什么情况下必须做什么 |
| 程序 | `.agents/skills/*/SKILL.md` | 具体怎么做、如何判断 |
| 校验 | `scripts/`、tests、CI、GitHub 评审策略 | 如何发现没做或做错 |

关键在第四层：脚本和 CI 检查“文档是否一致、格式是否合法、测试是否通过、PR 是否获批”，不检查“实施前是否形成了方案并获授权”。理解 DSH 的流程设计，先要接受这个边界。

## 一次变更的实际路径

1. 从 Issue 或对话得到目标，读根 `AGENTS.md`、`docs/architecture.md` 和相关 Agent Notes。
2. 按任务性质加载专项 Skill，例如简化调查、UI、错误处理、测试可靠性。
3. 直接修改代码，并按需在同一次变更中写或更新 Agent Note、README、JSDoc、升级指南或持久化记录。
4. 在本地运行与改动面相关的检查，不默认跑全量；全量和平台矩阵由 CI 承担。
5. 开 PR，引用 Issue，填写 PR 描述和 AI 使用情况。
6. CI 运行静态门禁、覆盖率、构建、快照等检查；人工评审按加权规则批准。
7. 合并后把 `proposed/` 记录改写为 `implemented/`，归档或合并被取代的记录。

“调查、形成方案”是规范期望的动作，但没有独立的完成产物或检查点，可以发生，也可以被跳过。第 3 步的“同步文档与记录”和第 7 步的“目录与状态一致”则都有脚本检查。

## 任务按风险分流

DSH 不要求所有任务走同一条路，而是按风险、争议和可逆性选择模式。规范没有给出文件数、包数或行数阈值，规模本身不触发提案。

| 情况 | 常见处理 | 强制程度 |
|---|---|---|
| 机械性、局部修改 | 直接改，Agent Note 豁免 | 规则明确豁免 |
| 局部缺陷修复、局部 UI | 直接改，可补一条 implemented 记录 | 无强制提案；UI 仍要设计评审 |
| 单包新功能 | 可以直接实施，完成后补设计记录 | 无强制提案 |
| 跨包重命名、架构调整 | 可能先写 proposed 记录，单独一个 PR 评审 | 规范建议，不强制 |
| 有争议的简化 | 用 `proposed/simplification` 记录候选和证据 | Skill 明确区分调查与授权，无门禁 |
| 持久化结构变更 | 必须写 acknowledgement，说明前驱结构、兼容决策和验证 | 有门禁 |
| 外部可感知的破坏性变更 | 同一变更内写升级指南 | 有门禁 |
| UI 或视觉变更 | 实际操作页面检查，广泛变更需设计或产品评审 | 有明确规则 |
| 官方插件新图标 | 落地前取得设计师批准 | 有明确规则 |

最清楚的表述在简化调查 Skill 里：调查得到的提案与实施授权是两件事，实施必须留在用户授权的范围内。这是程序层的判断标准，CI 无法验证。

## 人工关口在哪里

| 机制 | 发生位置 | 覆盖范围 | 是否在实施前 |
|---|---|---|---|
| PR 加权审批 | 合并前 | 所有变更，要求两分 | 否 |
| Issue 引用与标签策略 | 开 PR 时 | 非草稿、人类作者的 PR | 否，只保证可追溯 |
| UI 设计或产品评审 | PR | 用户可感知的 UI 与交互 | 否 |
| 图标设计师批准 | 资产落地前 | 官方插件的新 glyph | 是，仅限资产 |
| plan mode 的 Approve | 执行前 | 主动进入 plan mode 的会话 | 是，但需用户主动开启 |

唯一通用的执行前批准是 plan mode，而它是产品功能，不是仓库研发规则：需要用户主动进入，文档说明它只是引导，不限制工具，所有工具在计划阶段仍然可用。DSH 的文档建议用沙箱和审批提示做强制限制，而不是依赖 plan mode。因此不能把它当作“未批准不得改文件”的保证。

仓库规则里同样没有这些机制：没有“改代码前必须获得方案批准”，没有“改动超过 N 个文件必须先提案”，没有脚本检查“这个 PR 是否先有提案”，没有 `accepted` 状态，也没有默认开启的计划批准。

## 案例

| 案例 | 做法 | 说明了什么 |
|---|---|---|
| 仓库命名契约 | 先写 357 行提案（PR #2280），评审后修订，再实施 3281 文件的批量重命名（PR #2302），完成后标记 implemented（PR #2435） | 高风险、跨包变更可以在代码之前评审；评审确实改变了设计，例如新增 Binder 角色，把 ModelDirectoryRegistry 改为 ModelDirectoryResolver，把协议接口改成 TypertRegistryContract |
| PTC 的 scoped REPL | 37 个文件、新增 3399 行，单包功能，Agent Note 与代码同批直接以 implemented 创建（PR #8202） | 单包、边界清晰的大功能可以省略提案阶段 |
| 消息图片工厂 | 同一个提交里新增 proposed 记录和代码，次日把记录移到 implemented | `proposed/` 是记录状态，不是“代码尚未开始”的阶段 |
| 内置 timers/promises 简化 | 先实施尝试，测试证明前提不成立，再把提案标为 rejected（PR #679） | 生命周期不是线性流程，实现证据可以推翻提案 |
| 持久化类型变更 | 每个结构变更写 acknowledgement，机器检查记录完整性和类型兼容 | 机器能证明记录齐全，不能证明兼容决策合理，也不能证明有人审过 |

持久化文档把最后一点写得很直白：验证无法确认记录由谁编写、是否经过人工评审。这既是人工评审不可替代的证据，也是“门禁通过”容易被误读的边界。

## 结论的证据分级

| 结论 | 类型 |
|---|---|
| Agent Note 有 proposed、implemented、rejected 三种状态，目录、状态行与章节由脚本交叉检查 | 已实现机制 |
| 没有“实施前必须提案或批准”的通用门禁 | 未找到依据，已检查根规则、Skills、Scripts 和 CI |
| 提案的使用按风险判断，不按规模阈值 | 推断，来自两个规模相反的案例，以及规范中没有阈值 |
| PR 评审是事实上的最终授权边界 | 推断，仓库有评审策略文件，但分支保护设置不在仓库内 |
| 大范围直接实施在 DSH 中同样可能发生 | 观察，来自案例规模 |

本地无法确认的事项：PR 评论与批准人、GitHub 分支保护的实际情况、Agent 在会话中多常先调查、规范中“substantial”的判定标准，以及直接实施的记录是否在仓库外有过方案讨论。

## 对本项目的含义

1. **不要只复制目录。** `proposed/` 是文档生命周期，不是门禁；缺少“何时必须提案”的可判定条件和阻断点，它只会积累待评审记录。
2. **可迁移的是“同一变更义务加机器检查”。** 改契约必须改消费者，改结构必须写记录，否则脚本失败；这比提醒 Agent 记得更新文档可靠。
3. **把人工关口放在合并前，对大范围直接实施太晚。** 本项目因此把“调查默认只读、实施限定在任务范围”写成常驻边界，并明确目标不等于授权，而不是复制提案目录（[研发授权与任务边界](../../.agents/notes/implemented/process/2026-11-26-研发授权与任务边界.md)）。
4. **计划批准不能当硬约束。** 需要“未批准不得改文件”时，必须自己实现阻断，不能依赖 plan mode。
5. **按任务性质分流。** DSH 不为所有任务建统一流程，本项目同样用触发表的专项 Skill 替代统一研发流程，理由见 [第一版研发协作机制](../../.agents/notes/implemented/process/2026-11-26-第一版研发协作机制.md)。
