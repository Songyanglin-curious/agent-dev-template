# 防御性模式

本目录保存“修改某类工件之前必须核对”的缺陷模式。它回答的是怎样避免写错，不是系统具有什么契约，也不是为什么会做出某个决定。Agent 不需要通读事故历史，只需在修改对应对象前阅读这一页。

## 与相邻层级的分界

- **postmortem**：一次事故的经过、根因和当时的系统缺口，按时间叙述。
- **defensive-patterns**：从事故或重复评审中提炼、可在修改前执行的检查，不叙述故事。
- **core-guidelines**：写代码的设计规则，回答“怎样才能写好”，不按缺陷分类。
- **subsystems / 模块文档**：当前的类型、语义与契约，回答“系统是什么样”。

只有同时满足三个条件才新增模式：缺陷类型真实发生过或反复出现；判据能被评审者在代码或文档中识别；边界清楚，避免规则被过度套用。

## 组织

按工件（文档、脚本、数据、接口等）划分页面。按工件组织，使修改者只需加载与自己正在改的东西相关的一页。

## 模式格式

每条模式包含六个字段：

- **要求**：必须做到什么。
- **缺陷**：不这样做会出现什么错误，以及谁会受影响。
- **判据**：评审时如何在工件中识别违规。
- **边界**：适用范围的例外。
- **正确**：一个可执行的正确写法。
- **错误**：一个典型的错误写法。

## 使用

修改前按工件打开对应页面，逐条核对判据；评审时引用模式编号给出意见。模式与当前系统冲突时，先修改系统文档或该模式，不保留两种说法。
