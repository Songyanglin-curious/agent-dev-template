## DP-D1 同一事实的第二副本

**要求**：每个事实只在一个归属文档中维护。其他位置需要提及时，使用相对链接；确需一句摘要时，只写定位而不是细节。数字、默认值、类型定义、章节清单和命令参数不在第二个位置重现。

**缺陷**：源文档更新后副本保持旧状态，读者可能读到不权威的版本；搜索会同时命中两份互相矛盾的说明，维护者需要判断哪一份有效。副本越多，失效面越大。

**判据**：同一有辨识度的句子、表格或代码块出现在两份维护中的文档里；两处对同一路径、默认值或行为的描述不一致；修改归属方后，另一处的措辞已经过时。

**边界**：生成区域由生成器保证一致，不算副本；归档 Agent Note 是冻结快照，允许与当前文档不同；引用一小段原文作为论证对象时，注明来源并链接。

**正确**：

```markdown
类型定义见 [会话模型](../subsystems/session-model.md)，本模块只负责持久化与恢复。
```

**错误**：

```markdown
会话由 SessionRecord 表示，包含 id、createdAt、messages 三个字段……
```

第二段复制了子系统页拥有的类型定义；字段变更后它不会自动更新。

<a id="dp-d2-未经验证的操作性描述"></a>
## DP-D2 未经验证的操作性描述

**要求**：命令、配置片段、默认值、错误信息和平台差异，只有实际执行或由代码、测试、生成器提供证据后才能写入。无法验证时，写明证据归属方或省略该声明，不凭记忆和相似模块推断。

**缺陷**：读者按文档执行失败，浪费时间并降低对全部文档的信任；Agent 会基于错误前提继续修改，放大问题。

**判据**：文档中的命令在项目入口、脚本或帮助输出中不存在；声明的默认值与代码或配置不一致；示例没有对应的执行证据，且作者无法说明验证方式。

**边界**：`proposed/` Agent Note 可以描述尚未存在的命令，因为它明确是提案；外部系统的行为无法在本地验证时，链接外部文档并说明验证条件。

**正确**：

```sh
pnpm run verify-doc-budgets --list
```

该命令在 `package.json` 中注册，按文档所示执行并观察输出后写入。

**错误**：

```sh
pnpm run check-docs   # 项目中不存在
```

<a id="dp-d3-已实现记录中的提案语气"></a>
## DP-D3 已实现记录中的提案语气

**要求**：`implemented/` Agent Note 用现在时描述已交付的现实。计划、迁移步骤、验收清单和风险在交付时折叠进 `## Decision` 或 `## Consequences`；仍存在的限制写进 `## Testing` 或 `## Deferred`。

**缺陷**：读者无法区分“已经存在”和“计划做”；过时的计划看起来仍然有效，后续 Agent 可能按未实施的方案修改代码。

**判据**：implemented 记录中出现 `## Plan`、`## Migration plan`、`## Acceptance criteria`；正文用 "should"、"will" 描述当前行为；状态行是 implemented，但内容在请求批准。

**边界**：`## Testing`、`## Deferred`、`## Related` 是允许的现在时章节；提案阶段的历史动机可以保留在 `## Problem` 中，但不能保留提案式的行动清单。

**正确**：`决策：所有门禁共享 doc-tooling 的解析；拒绝各自维护正则。`

**错误**：`计划：下一步将把各门禁的解析统一到共享模块。`
