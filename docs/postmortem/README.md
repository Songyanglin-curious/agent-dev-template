# postmortem

本目录保存事故复盘：一次故障的现象、根因、为什么原有防护没有发现，以及为防止复发增加的保障。复盘的按时序叙述是证据，不是教学顺序，也不作为日常任务清单。

## 什么时候写

只有同时满足以下条件的故障值得复盘：

- **隐蔽性**：机制不明显，谨慎的工程师也难以立即发现。
- **系统性**：暴露了测试、工具、文档或工程约定的缺口，而不只是一次笔误。
- **重复发现成本高**：这次已经花费大量时间排查，未来可能再次付出同样代价。

普通缺陷修复、性能调整和已知边界内的失败不写复盘。复盘必须产出可执行的保障：一条防御性模式、一条核心准则、一个检查脚本、一个测试或一个 cookbook 步骤；没有保障的复盘只是叙述。

## 结构

每份复盘包含：`摘要`（一到两句）、`影响`（用户或系统可观察的后果）、`时间线`（关键事件与发现顺序）、`根因`（机制层面的原因，不是人名）、`为什么没有发现`（测试、评审、工具、文档各自的缺口）、`保障`（新增或修改的检查，链接到归属方）、`相关记录`（Agent Note、持久化记录或外部链接）。

`保障` 中的每一项都必须指向真实存在的文件或命令；尚未落地的措施写在 `暂缓措施` 中并说明触发条件。
