# Agent Note: 文档同步的触发与检查

Status: implemented

## Problem

文档标准只能约束“文档应该写成什么样”，不能保证一次代码改动同步了它所属的文档。此前的做法依赖 Agent 在任务结束时自觉回忆，结果是指令写了但经常被跳过；而积累的准则、防御模式和 cookbook 也不会在需要时被加载。需要把同步变成研发流程中的必经步骤，并让遗漏在交付前以具体清单的形式暴露出来。

## Decision

三个机制分担“什么时候做、怎么做、做没做”，每个机制只承担一种职责。

根 `AGENTS.md` 的触发表列出本仓库的改动类型及其必须同步的归属方，例如修改门禁脚本要更新文档门禁子系统页，产生长期决策要写 Agent Note。触发表只写“改动 → 归属方”，不写操作步骤。

`dev-workflow` Skill 规定一次非机械性研发任务的完整流程：接收输入、定位影响面、判断是否立提案、实施、同步文档、沉淀工程知识、运行验证、交付报告。流程中的每一步指向归属方，不复制那些文档的规则。

`verify-change-docs` 读取 `scripts/change-doc-rules.json`，用 Git 取得本次改动的文件集合，输出每个改动路径对应的文档归属方。`remind` 规则始终只提示；`require` 规则只在 `--strict` 下要求归属文档也出现在本次改动中。`--strict` 不提升 `remind`，所以当前没有 `require` 规则时它没有实际强制效果。它把“回忆哪些文档可能受影响”变成“逐项核对生成的清单”。

现有的结构门禁继续承担可机械判定的部分：Agent Note 生命周期与格式、归档冻结、模块摘要与限制、模块组表、子系统关联、链接与锚点、单段一行、提交号引用、字数预算、持久化记录和生成区域。Markdown 结构门禁覆盖模块 README；模块文档仍按 `kind` 发现，未声明元数据的 README 不进入检查，由评审发现。`pnpm run test:docs` 串联这些检查，并在末尾运行变更影响清单检查。

`pnpm run test:gates` 在临时工作区验证坏链接、缺失预算文档、无效基线、错误 Note 格式和 `require`/`--strict` 语义。`.github/workflows/docs.yml` 在 push 和 pull request 上运行三个测试入口，pull request 额外以 `--strict` 运行变更影响检查。CI 能发现问题；把工作流设为必需检查才阻止合并。

## Alternatives considered

**只靠根 `AGENTS.md` 的更长指令。** 指令越长，Agent 越容易只读开头；而且每次任务都要重新解释同样的流程。把流程放进 Skill 可以让主上下文只保留触发条件。

**用 Git hooks 强制每次代码改动都修改文档。** 绝大多数改动（重命名、格式化、内部重构）不需要文档变化，强制映射会产生大量假失败，最终被跳过或被无意义地满足。

**把 `verify-change-docs` 做成纯失败门禁。** 语义判断无法可靠自动化：同一条规则下的小修也可能不需要文档更新。默认提示加少量显式 require 规则，既保留可见性，又避免假失败扩散。

**在 `--strict` 下把所有 `remind` 提升为 `require`。** 这会让每次脚本小改都要求同步所有归属文档，制造无意义的文档更新。严格模式只执行已经明确建立的 `require` 规则。

## Consequences

收益是同步从“记住要改哪些文档”变成“核对一份由改动生成的清单”；触发表、Skill 和规则文件各自有唯一归属，修改其中一处时其他位置通过链接而不是复制保持一致；失败路径测试证明门禁能够拒绝违规，而不只是正常输入下通过。

代价是触发表和变更影响规则需要随项目演进维护，规则过宽会产生噪音，过窄会漏掉影响；`verify-change-docs` 只按路径匹配，不能判断改动是否真的影响文档语义，最终仍要人或 Agent 读一遍清单。当前没有 `require` 规则，严格模式没有强制效果；这是有意留空，等能够客观判断“必须同步”的变化出现后再添加。

另一个限制是 `verify-change-docs` 依赖 Git 基线。无 Git 或非 Git 仓库时它明确跳过并说明；显式基线无法解析时以非零退出并报告基线，不抛 Node 堆栈。它主要服务于提交前和 CI 中带 `--base` 的运行，而不是替代结构门禁。模块文档按 `kind` 发现，未声明元数据的 README 由评审兜底。

## Verification

`pnpm run verify-change-docs` 在存在改动时打印归属方，把归属文档加入变更后显示 `updated`；默认不因 `require` 规则失败，`--strict` 下才失败。`pnpm run test:gates` 覆盖这些分支和环境错误；CI 在 push 与 pull request 上运行三个入口，pull request 额外运行严格模式。`dev-workflow` 的交付报告要求复述清单结果，避免把退出 0 当成文档已同步。
