# Agent Note: 轻量研发任务管理

Status: implemented

## Problem

此前只明确区分了原始输入、研发任务和 Agent Note 的职责，却把任务层留给对话和临时说明。简单任务这样做没有问题，但复杂任务跨多轮后，目标、范围、验收、进展和最终交付容易散落在对话、提交和最终回复中；没有可引用的任务记录，也无法机械检查状态和归档。

直接引入 Issue 系统会带来编号、标签、优先级、负责人、评论和自动状态流转，超出本项目的本地研发规模。需要的是把“这次做什么”落成轻量文件，同时保留原有授权边界和 Agent Note 的独立职责。

## Decision

新增 `研发任务/`，一项任务一份 Markdown，不建每任务目录：

```text
研发任务/
├── README.md
├── 进行中/
└── 归档/
    ├── 已交付/
    ├── 已放弃/
    └── 已替代/
```

任务文件使用 `YYYY-MM-DD-<标题>.md`，YAML 只保留 `status`。状态与目录必须一致：`进行中` 在 `进行中/`，`已交付`、`已放弃`、`已替代` 分别在 `归档/` 下对应目录。状态变化时移动原文件，不复制；移动后修复相对链接。

每个任务包含目标与背景、关联输入、范围与验收、进展、最终交付、验证、遗留问题。`已放弃` 额外记录原因；`已替代` 额外链接替代它的新任务。任务通过相对链接引用 `研发输入/` 和 Agent Note，不复制原文；任务可以没有外部输入。

新增 `task-management` Skill，按需创建、推进、交付、放弃和替代任务，不建立统一研发流程，也不要求普通问答创建任务。新增 `verify-tasks` 检查目录、文件名、`status` 与目录、必需章节、终态记录、替代引用和本地链接；它不判断任务是否真正完成。

本记录取代此前“研发任务只存在于对话、不建常驻任务目录、不建立交付状态机”的任务层决定；原有调查只读、实施范围和授权边界继续有效。Agent Note 仍只保存长期决策理由，不承担任务进度。

## Alternatives considered

**继续只靠对话和最终回复。** 简单任务足够，但复杂任务无法稳定追溯范围、验收和交付，也无法检查状态和归档。

**采用 Issue/PR 任务系统。** 编号、标签、优先级、负责人、评论和自动状态流转会引入与本地研发规模不相称的管理负担。

**每项任务建一个目录。** 任务文件通常很短，独立目录会增加空目录、路径深度和移动成本；一份 Markdown 足以同时承载说明、进展和交付。

**把状态只写在文件名里。** 文件移动后仍需要人类可读的状态字段和机械检查；YAML `status` 与目录交叉校验更直接。

**让 Agent Note 兼任任务记录。** 会把长期决策理由和短期进展混在一起，违反 Note 的职责边界。

## Consequences

复杂任务现在有稳定入口和终态记录，输入、任务、Note 可以通过链接追溯；简单任务仍可以直接在对话中完成。代价是任务移动时必须修复相对链接，任务文件需要随进展维护；门禁只检查结构，不能证明任务真的完成或交付质量合格。

任务目录不是 Issue 系统：没有编号、优先级、负责人、标签、评论、看板或自动状态机。终态任务不回到 `进行中/`；需要继续工作时新建任务，并按实际情况让旧任务进入 `已替代/`。

## Testing

- `pnpm run verify-tasks` 检查实际任务目录；当前没有任务时报告 0。
- `pnpm run test:gates` 覆盖任务有效记录、状态与目录不一致、缺少章节、断链、放弃原因和替代引用。
- `pnpm run test:docs` 校验任务 README、Skill 和架构链接。
- `pnpm run test:notes` 校验本记录和旧记录的交叉引用。
