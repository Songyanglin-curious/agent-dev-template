# Agent Note: Skills 与 Scripts 差距盘点

Status: proposed

## Problem

第一版已实现 `change-scope`、`code-review`、`pre-push-checks` 和 `project-onboarding`，并修正 `verify-repository-references` 对 `研发输入/` 的扫描范围。剩余能力仍有缺口：持久化兼容、门禁失败路径、零语料门禁、文档同步强制力、模块/子系统验证、任务说明、发布部署和 Skill 调用证据。

现在直接补齐这些剩余能力会扩大改动范围，也容易在没有真实使用场景时制造空 Skill、空检查或空文档。需要先把差距登记为候选，由维护者判断优先级和触发条件。

## Proposal

登记以下剩余候选，不代表本轮实施：

| 候选 | 分类 | 当前状态 | 缺口 | 建议方向 |
|---|---|---|---|---|
| 持久化兼容 | 待研究 | 有三类记录模板和 `verify-persistence-records` | 0 条实际记录、无提取器、无失败路径测试 | 按真实项目的持久化技术补工具和记录，不在模板阶段假装完成 |
| 门禁失败路径测试 | 已确认缺口 | `test:gates` 有 15 个用例；8 个门禁有失败路径测试，6 个门禁有空语料可见性测试（有重叠） | 多个门禁只有正向通过，没有反向用例 | 优先补高风险门禁的失败路径，并增加“新门禁是否有测试”的检查 |
| 零语料预期基线 | 待研究 | 六个门禁在空语料下报告 0，并有空语料扫描测试；仍允许真实空集，没有预期数量或异常缩小检测 | 无法区分真实空集与 glob/排除规则错误 | 需要时设计预期基线或按门禁设零语料策略；本轮不强制失败 |
| 文档同步强制力 | 已确认缺口 | 3 条规则只覆盖 scripts、Note 规则和 package，且全部是 `remind`；`--strict` 无实际效果 | 根 `AGENTS.md`、docs、Skills 的变更没有归属规则；文档遗漏不会使 CI 失败 | 先选少量可客观判定的 `require` 规则，或明确保持提醒模式 |
| 模块/子系统验证 | 已确认缺口 | 只有 `scripts/README.md` 一个模块和一个子系统页 | 模块组、模块限制、子系统关联缺少真实语料 | 选一个真实试点，验证后再扩大门禁 |
| 任务说明与输入追溯 | 待研究 | 已有 `研发输入/` 和 Agent Note 规则 | 没有任务说明格式；复杂任务的多轮范围容易失散 | 等真实复杂任务出现重复需要，再定最小任务说明 |
| 发布与部署 | 暂不需要 | 没有通用机制 | 发布/部署/迁移的授权、检查和回滚未抽象 | 由具体项目按自己的发布流程实现，不在模板阶段建通用 Skill |
| Skill 调用证据 | 暂不需要 | 没有会话日志或调用记录 | 无法确认 Skill 是否被实际加载 | 暂不作为门禁；先靠任务结果和交付说明观察 |

分类标准：

- **已确认缺口**：已有证据表明当前机制不能覆盖，且与当前目标直接相关。
- **待研究**：需要真实场景或 DSH 对照，暂不实施。
- **暂不需要**：当前模板阶段没有通用需求，或依赖具体项目形态。

本轮已实现：`change-scope` 工具；`code-review`、`pre-push-checks`、`project-onboarding` Skills；`verify-repository-references` 排除 `研发输入/` 并补测试；空语料计数可见性由六个门禁输出和 `test:gates` 回归测试覆盖。Git 推送与历史边界已写入 `pre-push-checks`，仍需真实远端验证。

这些候选的共同边界是：只有出现明确触发场景、需要多步判断、会重复出现，并且现有规则或文档无法承载时，才建立新的 Skill 或 Script。一个风险点不自动对应一个 Skill。

## Alternatives considered

**一次性补齐所有候选。** 这会把差距盘点变成大规模建设，超出当前验证能力；多数候选还没有真实使用场景。

**为每个风险点建一个 Skill。** 会把一个总流程拆成多个薄 Skill，增加维护面，却不一定增加约束力。

**把候选写成任务清单。** 任务清单会腐烂，也会让 Agent Note 承担任务管理。这里只记录能力判断和触发条件，不记录进度。

**只保留根规则，不登记差距。** 删除 `dev-workflow` 后，某些能力会无声消失；登记候选可以让维护者看到缺口，但不立即实施。

## Acceptance criteria

- 维护者审阅候选表，决定哪些进入下一步、哪些暂缓、哪些不采用。
- 被采纳的候选在实施时具备明确触发场景、归属方、验证方式和失败处理。
- 未被采纳的候选不转化为空 Skill、空目录或空检查。
- 本轮已实现 `change-scope`、`code-review`、`pre-push-checks`、`project-onboarding`；其余候选不实施。

## Risks

- 候选表可能被误读为路线图或任务清单；它只是待评审的能力盘点。
- 某些候选依赖具体技术栈或项目形态，在模板阶段无法给出通用实现。
- 如果长期不审阅，候选表会过时；它需要随真实研发活动更新或删除。
- 现有门禁的零语料和失败路径缺口可能在候选落地前继续存在，不能把当前绿色误认为完整覆盖。
