# 文字标准

写到足以保留契约，然后删除推理过程记录、重复和修饰。契约是调用方、被调用方、实现方、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容性承诺。本 skill 负责编辑判断和必需的覆盖范围；页面放置、字数预算和文档门禁使用 [doc-writing](../doc-writing/SKILL.md)，查找并修复推理过程记录泄漏使用 [trim-cot-leakage](../trim-cot-leakage/SKILL.md)。它是指导，不是脚本。

把 `contract`、`boundary`、`shape`、`surface`、`gate` 和 `vocabulary` 当作使用前需要核对的术语，而不是禁用词。先问：确切的规则、API、字段集合、类型、校验、时间点、组件拆分或失败情形，是否把该事实表达得更好。当某个术语精确命名了技术对象——包括调用方/被调用方契约以及安全/进程边界——就保留它。

注释描述代码无法表达的、非显而易见的契约或理由；它们不复述代码已经隐含的内容。

## 输入与排除范围

要求显式给出 `scope`。缺失时报告所需输入并停止；不要推断出全仓库范围，也不要开始访谈。

接受 `mode: automatic | interactive`，默认是 `automatic`。只有当用户明确要求提问或校准时，才进入 interactive 模式。

`mode` 控制提问，不控制写作权限。评审和审计任务只报告发现，不做编辑；显式要求 write、fix 或 trim 的任务才应用明确的改动。

文字评审和编辑排除 `.agents/notes/archived/`：归档的 Agent Note 是冻结快照，检查某个确切目标只用于理解历史上的入站引用，绝不是为了现代化其文字或出站链接。

如果项目存在第三方引入目录（例如 `vendor/`），始终排除它，即使请求的范围是整个仓库；不要跟随符号链接进入其中。把排除规则放在包含 glob 之后，以免后续的 include 重新把它纳入：例如 ripgrep 命令以 `--glob '!vendor/**'` 结尾，Git 命令给出显式的 `:(exclude)vendor/**` pathspec。如果请求的范围只有该目录，报告没有符合条件的文件。

把生成的 catalog、快照和 fixture 当作衍生产物。编辑前追踪每一个消费方：源 JSDoc 可能同时供给一个生成式的用户可见 catalog。先编辑所属源码或场景，再重新生成所有衍生产物。当生成器从归属方的文字中抽取摘要时，要让被抽取的句子在该表面上自成完整句。遵循[轻量常规路径](../../../docs/AGENTS.md#writing-rules)。

## 保留完整命题

编辑前，识别段落中的每一个命题。保留每一项相关的：

- 执行者和动作；
- 条件、时序和先后顺序；
- `must`、`may`、`never` 这类情态；
- 否定性保证和例外；
- 归属、副作用、失败模式和后置结果。

只有当每个事实从句都存活、且结果更清楚时，才删除形容词、重复和叙述。仅仅字数更少不算改进。

在使用位置保留完整的本地契约：调用方或维护者在那里需要的行为、失败、归属和后果。架构、理由、算法、历史或扩展示例则积极地链接到所属文档。一种解释只有一个家；必要的契约事实可以在本地重复。

当省略某项非显而易见的理由有可能导致误用或不正确的简化时，保留该理由。否则只陈述后置结果，并链接理由所在处。

## 按文字位置要求的覆盖范围

这不是单向的删减过程。当代码、类型和结构无法传达下面某项必需的契约时，要补充或恢复文字。当这些事实在本地已经显而易见时，不要添加注释。

- **公开 JSDoc：** 记录调用方可见的返回值区别、抛出或拒绝、副作用、归属、时序、取消和持久性。
- **内部注释：** 为跨位置结构和显而易见的复杂本地结构提供定位，包括不变量、竞态顺序、归属、安全边界和令人意外的失败行为。删除控制流叙述和代码复述。
- **模块注释：** 说明模块的角色、依赖、职责和非显而易见的架构选择；把架构选择链接到其所属解释。
- **测试：** 只解释非显而易见的测试设计——为什么需要某个 fixture、断言、平台适配、真实入口路径或间接观察。删除走查和清单。
- **Cookbook：** 包含前置条件、必需操作、真实入口路径、可观察的验证和简明警告。
- **模块文档：** 包含消费方契约：能力、使用方式、配置、语义、失败、限制、扩展点和用户可见效果。引用由该模块负责的稳定用户可见文本；链接生成目录和跨模块归属方。保留持久性缺口和维护者陷阱，而不是普通的清理清单。遵循[模块文档模板](../doc-writing/templates/module.md)。
- **Agent Note：** 保留独有的理由、机制、替代方案、后果、已交付的验证证据和具名覆盖缺口。已实现的 Agent Note 用现在时陈述已交付的现实；删除计划清单，而不是删除支撑决策的证据。
- **复盘：** 保留事件序列、证据、因果链、影响和预防措施。删除不确立因果关系的重复说服或实现细节。
- **Skill 与 agent 指令：** 写明行为护栏和显式的范围限制，例如“guidance, not a script/checklist”。保持工作流程简洁，并链接其真相来源。
- **示例与配置注释：** 解释访问限制、非显而易见的接线或加载顺序、安全立场、重放行为、例外和可能的误用。不要叙述配置本身已经展示的条目。
- **Prompt 与可见字符串：** 把措辞当作行为。要同时检查文本、无障碍名称、tooltip、placeholder 和格式模板，以及由所属行为测试锁定的输出。英文 UI 文案使用 sentence case：只大写首词、专有名词以及 `Chrome DevTools`、`Git`、`MCP` 这类产品名（写 `Git worktrees`，不写 `Git Worktrees`）；中文文案保留自己的惯例。为可见文本更新所属的可运行快照或证据；如果授权范围内没有所属场景，保持措辞不变并报告该延期，不要悄悄把它并入只改文字的编辑。
- **诊断信息：** 说明失败的主体或路径、违反的规则，以及不显而易见时的修正方式。删除内部执行叙述。

保留可搜索的机制名称，以及有意义的情态、时间或否定强调。只规范化装饰性强调。

## 工作流程

1. 确认范围、模式、当前分支或 PR 基线，以及适用的 `AGENTS.md`。不要检查无关分支。
2. 在判断一段文字之前，先阅读[文档标准](../../../docs/AGENTS.md)和所属代码或文档。需要校准或不熟悉的情形，阅读[精炼示例](references/examples.md)。
3. 检查请求的范围，而不只是最大的文件。用搜索和字数统计找出候选，再按语义判断各段落。
4. 把每个候选项归类为保留、补充、删减、恢复、重构或延期。只有当任务授权编辑时才应用明确改动；不要为了满足删除指标而制造编辑。
5. 先更新归属方，再更新衍生产物。学到新规则后，重新检查类似段落。
6. 运行针对性的相关检查、`pnpm run test:docs`、`git diff --check`，以及可见字符串的行为测试。涉及 Agent Note 时运行仓库的 Agent Note 门禁。
7. 报告检查过的范围、明确的改动、刻意保留的内容、延期处理的情况，以及实际运行的检查。

## 边界情形判定

只有当至少两个版本都满足完整命题规则、但要在已接受的原则之间取舍，且本 skill 尚未解决该取舍时，才算边界情形。存在唯一保命题答案的改写不是边界情形。

在 automatic 模式下，获得授权时应用明确改动，并报告真正的边界情形而不提问。不要为了让工作推进而弱化命题。

在 interactive 模式下，把类似段落归到同一条支配原则之下。给出两到三个可行版本，推荐其中一个，并说明事实或结构上的差异。不要提供劣质干扰项。使用用户指定的渠道；通过行内评论校准 PR 时，把推荐版本放进 diff，并把备选方案附在该行上。

用户决定之后，把该原则和各版本提炼进[示例](references/examples.md)，不附带 PR 历史或评审者叙述，并把学到的规则应用到范围内所有类似段落。
