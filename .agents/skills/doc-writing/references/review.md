# 评审标准

## Summary

评审文档要看读者能否完成某个结果，而不是看模板标题是否齐全。对照代码和测试核验文字，保留精确的约定，让模块文档对使用者和维护者都有用。运行当前仓库具备的门禁，如实报告按项目实现的检查，并按依赖表说明现状。

## 新人测试

一个没有仓库背景的专业工程师，在读完三到五个互链页面后应能回答：产品或功能做什么、如何安全地运行或使用、它的状态存放在哪里、哪个组件负责它、它如何失败、以及在哪里修改它。如果读者仅仅为了发现公开流程就必须查看源码，就补回缺失的解释。如果读者必须吸收无关的内部细节，就把这些细节移得更深。

## 证据评审

对照最强的归属方检查每一项实质性陈述。名称和入口点用模块 manifest 与入口文件，API 约定用公开类型和 JSDoc，行为用运行时代码，已演练的失败路径用测试，穷举清单用生成目录，理由用活跃的 Agent Note。绝不要把旧的 README、讨论或报告看得比当前代码和测试更权威。

对每一项操作性声明——命令、配置片段、默认值、错误消息、平台差异——证据是执行它，而不是阅读它。在页面陈述其行为之前，针对当前 checkout 执行确切的命令或加载确切的配置；只引用观察到的输出、警告和失败。依赖不可用凭据或网络的声明，要写出核验归属方，而不是断言行为。对既有页面，与默认分支的最新提交比较，并对照代码重新核验过时的说法。

评审接入指引前先判定模块形态：从 manifest、入口文件和配置声明读出它是常驻服务、进程内库、插件、命令行工具还是一次性脚本。拒绝为其他形态编写的安装或启动指引：没有安装机制的模块不得出现安装命令，可执行形态不得写成库用法。

只有当陈述能帮助目标读者行动、推理或避免误用时才保留它。把理由、历史、测试走查、重复目录和无关的模块细节移到它们的归属方。

## 模块文档评审

要求以下内容，但不强制统一的内部标题集合：

- 可搜索的 YAML 元数据，包含精确的 `description` 和机械推导出的 `kind: module`；
- 三到五句、最多 100 个词等量的 Summary（英文按空白分词，中文按每两字一个词等量），说明该对象为其用户或 agent 读者做什么，并带有链接的 `Table of Contents`；
- 受控的页面文字：明确的执行者、稳定的术语、直接的动作、分离的指令与条件，以及不变的情态；
- 何时选择或避免该模块，以及与相邻模块、替代方案的分界；
- 存在时给出最小的安全使用路径：有安装机制时是经过验证的安装命令，没有时为实际的调用、加载或启动方式，绝不套用不适用的形态；
- 与使用方相关的可观察行为、失败、持久性、并发、安全性、性能和模型可见效果；
- 职责边界：本模块负责什么、不负责什么，以及相邻归属方的链接；
- 概念层面的内部设计——整体设计、架构、粗线条数据流和依赖方向——这些无法从公开类型低成本恢复，并附源码导航以提供精确细节；依赖全貌链接架构文档；
- 当前限制与明确延后的工作，每条说明对调用方或维护者的后果；
- 相邻文档确实有实质帮助时，提供面向新人的 Further Exploration；
- 最后的非权威 Dev Note，作为半成品想法、草稿和未定方向的唯一存放处。

不要复述 JSDoc 或生成目录。链接归属方，只解释本地需要的决策或关系。模块 Summary 描述读者可见的能力，而不是内部角色、注册项或组件拆分；除非读者会直接在配置、命令或公共 API 中使用，否则省略源码标识符。拒绝任何叙述内部细节（函数主语、事件流、数据流）的面向用户章节，也拒绝任何只枚举 API 而不解释概念的折叠区。

## 模块组文档评审

模块组文档是导航与分工地图。评审它是否让读者找到正确的模块文档，而不是检查它是否复述了模块细节：

- 可搜索的 YAML 元数据，包含精确的 `description` 和 `kind: module-group`；
- 三到五句的 Summary，说明这组模块提供什么能力、读者能用它完成什么，以及主要边界；长度上限与模块 Summary 相同；
- 模块组定位：面向什么场景、何时使用，以及与相邻组或替代方案的分界；
- 模块表：一行一个直接下属模块，链接指向真实存在且 `kind` 为 `module` 的文档，职责文字说明贡献而不是内部实现；
- 组合关系：依赖方向、协作顺序，以及这些关系对选择、配置或修改的影响，而不是调用细节；
- 职责边界：组负责什么、不负责什么，并链接模块文档或其他归属方；
- 不含使用方式、行为契约、配置、限制和内部设计——这些属于模块文档；
- 导航链接全部有效，最后的 Dev Note 明确为非权威。

模块组按需使用。拒绝为单个模块创建模块组文档，也拒绝强制每个父级目录都建立 README。

## 语料审计

阅读归属约定文件本身，不要转述摘要：[docs/AGENTS.md](../../../../docs/AGENTS.md) 负责层级、教程/参考形态、分类法、预算和冗余清单；[.agents/notes/README.md](../../../notes/README.md) 负责 Agent Note 生命周期；[根 AGENTS.md](../../../../AGENTS.md) 负责常驻指令。审计和编辑时排除 `.agents/notes/archived/`——归档笔记是冻结的历史。

对范围内每个面向人的文档应用标准的编写顺序（不适用于 Agent Note）：定位文档并说明其自身主题；设定允许的细节层级，把更深入的解释移到负责它的子页面并用链接关联；按预期用途而非路径判断它属于教程还是参考；对教程，按前置条件和难度排列概念；拆分体量较大的混合形态。

然后检查放置约束：生成目录和生成区域绝不手工编辑；移动必须原子完成，并在同一次改动中修复所有入站链接、索引条目和生成产物；同一事实出现在两处时只保留一个归属方，其余改为链接。

结构检查之后，用成本最低的检查手段先排查 [docs/AGENTS.md](../../../../docs/AGENTS.md#冗余清单) 的冗余清单。用 grep 搜索有辨识度的短语以找出重复的规则；把手写的目录和状态清单替换为其权威归属方；从已实现的 Agent Note 中删除迁移计划和将来时态的需求描述；与当前代码、测试和配置比对，找出描述旧行为的过时段落。推理过程记录的清理使用 [trim-cot-leakage](../../trim-cot-leakage/SKILL.md)；如果删除文字改变的是承诺的行为而不是对行为的解释，先提出行为变更，而不是在文档评审中直接降低承诺。

保留每一条承重规则，最好是一到三行，再加一个指向其理由的链接；不要仅仅为了转移一次性推理而新造一段解释。

## 字数预算

`scripts/doc-budgets.manifest.json` 设置常驻文档的字数上限，`pnpm run verify-doc-budgets --list` 列出当前预算和实际字数。上限约束每会话都要读取的常驻文档——根 `AGENTS.md`、各级子树 `AGENTS.md`、架构概览这类入口文档——具体目标值登记在 [docs/AGENTS.md](../../../../docs/AGENTS.md#wordcount-budgets)。

门禁变红时按固定顺序处理：

1. **迁移**属于其他层级的内容；必要时留一行链接。
2. **压缩**属于此处但可以更短的内容。
3. 只有当文字确实需要空间时才**上调**上限，并说明 manifest 改动的理由。

上限是护栏，不是削减目标：达到或低于目标时至少保留 5% 余量；高于目标时冻结上限，直到迁移或压缩把文档降到目标以下；只有文档仍有空间时才下调上限。不要对穷举式参考套用统一的字数上限——衡量入口路径长度、为查一处而扫过的无关材料、最大章节、标题数量和页面大小，检索成本高时按既有的领域归属方拆分。

计数口径是 CJK 字符逐个计 1、其余按空白分词；`verify-doc-budgets` 的实现与失败信息都按此口径。模块 Summary 使用词等量口径（中文每两字一个词），见[模块文档评审](#模块文档评审)。

## 验证

验证的是受影响的格式，而不仅仅是 Markdown 语法。一个强承诺需要一个针对性的有效 fixture，以及一个能证明顶层门禁会失败的无效 fixture。

- 文档元数据：运行 `verify-doc-metadata`。它解析 YAML，把 `kind` 映射到模板，并拒绝 `name`、`audience`、`tags`、`i18n` 和广告式 description。
- 模块文档：运行 `verify-module-readmes`。它限制 Summary 的词等量长度，要求规范的 `已知限制与暂缓工作` 章节或带理由的白名单条目；白名单过期、理由为空，或白名单项仍带限制章节都会失败。
- 模块组文档：运行 `verify-module-groups`。模块表链接必须指向真实存在且 `kind` 为 `module` 或 `module-group` 的文档；模块自己的使用方式、行为契约、配置、限制和内部设计章节被拒绝。
- 子系统关联：运行 `verify-subsystem-pages`。每个模块组（没有模块组时用模块）必须链接至少一个存在的 `docs/subsystems/*.md`，或登记带理由的豁免；豁免过期或豁免项仍然链接都会失败。
- 源码文档引用：运行 `verify-doc-refs`。源码注释中的 `docs/*.md` 与 `.agents/notes/*.md` 路径必须存在。
- 持久化记录：运行 `verify-persistence-records`。它校验三类记录的位置、frontmatter、必需章节、唯一机器声明块、digest 语法、前驱引用和格式 schema 区域；提取与刷新工具按项目实现。
- 生成区域：运行 `verify-generated-docs`。区域标记必须成对且不嵌套；每个含生成区域的文档必须在 `scripts/generated-docs.manifest.json` 中声明生产方。
- 链接、换行、引用与预算：运行 `pnpm run test:docs` 的其余部分；任一项失败都要修到通过。
- 教程：实际走一遍文档中的入口路径，或明确指定人工核验归属方。
- 生成式参考：运行确定性的新鲜度检查，并报告检索规模指标。
- Agent Note：运行仓库现有的分类、格式和归档门禁。

完整入口是 `pnpm run test:docs`（上述十一个门禁依次运行），随后运行 `git diff --check`。Agent Note 改动另跑 `pnpm run verify-agent-note-classification`、`verify-agent-note-format`、`verify-archived-agent-notes`。表中标为「按项目实现」的项目，在建立前不得声称已经运行。
