# 评审标准

## 摘要

以读者能否达成实际结果评审文档。依据代码和测试核对正文，完整保留契约，使包 README 对使用者有用，同时为维护者提供足够的实现细节。运行仓库当前的校验。`session-persistence-jsonl` 的双语 README 是格式范例。

## 新人阅读测试

一位不了解仓库的专业工程师应该能通过三到五个互相链接的页面回答：产品或功能做什么，如何安全使用，状态存在哪里，由哪个组件负责，如何失败，以及到哪里修改。如果读者必须查源码才能弄清公开使用流程，补上说明。如果必须阅读无关内部细节，移到更深层的文档。

## 证据审查

使用最有权威性的来源核对每项重要声明。包元数据定义名称和入口，公开类型和 JSDoc 定义 API 契约，运行时代码定义行为，测试证明已覆盖的失败路径，生成目录提供详尽清单，仍在维护的 Agent Note 解释理由。早期 README、讨论和报告均不得优先于当前代码和测试。

CLI 命令、配置片段、默认值、错误信息和平台差异等操作声明都需实际执行取证。在当前检出版本运行确切命令或挂载原样配置之后，才可描述其行为。只引用观察到的输出、警告和失败。缺少密钥或网络时，指出负责验证的人或组件。已有页面应与最新 `origin/master` 对照，并按代码重新验证过时声明。

审查安装说明前先确定包类型。`package.json` 中的 `dsh.bundle.patch` 声明标识捆绑包，通过 `dsh plugin --profile <name> add <package>` 安装，只有这种类型由该命令激活为一层。导出 `apply` 或默认导出服务的是插件，通过一条 `cordis.yml` 配置挂载。普通模块 API 属于库，作为依赖使用，无独立安装路径。确认说明符合实际包类型。

只保留能帮助目标读者行动、判断或避免误用的文字。理由、历史、测试过程、重复目录和无关包的细节应移到各自负责的文档。


## 包 README 评审

要求具备下列内容，具体内部标题可按文档用途确定：

- 可检索的 YAML 元数据，含准确的 `description` 和按规则推导出的 `kind`（`package-group`、`package-reference`、`package-library` 或 `package-bundle`）。
- 三到五句英文 Summary，按 `wc -w` 计数最多 100 词，说明用户或 Agent 用该包能做什么，并配有可点击的 Table of Contents。
- 受控英语，明确主体、稳定使用术语、选用直接的动词、拆分指令与条件，并保留约束强度。
- 何时应选用或避开该包。
- 可用时给出最小而安全的配置或使用路径。捆绑包采用已验证的 `dsh plugin` 安装路径，库说明消费者入口。只有真正支持配置档安装的包才写相应说明。
- 使用者相关的可观察行为、失败情形、持久性、安全和性能限制。
- 面向开发者的责任归属、数据和生命周期设计，保持在总体设计、架构及数据流概况的层次，说明难以直接从公开类型得知的信息，并链接代码以供查阅确切细节。
- 包策略规定的 Model Experience 和 Known Limitations 章节。
- 邻近文档确有帮助时，向新人提供 Further Exploration。
- 结尾的非权威 Dev Note，集中存放未成形的想法、草稿和未定方向。

链接 JSDoc 和生成目录的负责来源，只在本页说明所需的判断或关系。包摘要讲读者可见的功能，省略 Cordis 角色、注册项和内部组件。只提读者在配置、命令或公开 API 直接使用的源码标识符。面向用户的章节不要叙述函数、事件流和数据流等内部实现。折叠的开发者部分应解释设计思路，避免逐一罗列 API。


## 范例

`session-persistence-jsonl` 的双语 README（[英文](../../../../packages/session/session-persistence-jsonl/README.md)、[中文](../../../../packages/session/session-persistence-jsonl/README.zh.md)）展示了此格式的实际用法。它包含可检索的 YAML，其 `kind` 选择包参考规范，还包含四句 Summary、可跳转的 Table of Contents、涵盖选型、配置、布局、持久性和读取的用户用法、用 GitHub 原生 `<details>` 折叠的开发者设计与存储细节、Further Exploration、规范规定的 Model Experience 和 Known Limitations，以及结尾的 Dev Note。包 README 和跨包页面可参考它的结构、证据标准与双语对齐。每条声明都以负责的源码和证据为依据。


## 验证

迭代时先运行最小范围的检查，再运行常规文档校验：

```sh
pnpm run test:docs
pnpm run verify-translation-pairing --write <pair>
pnpm run doc-sync
pnpm run lint
git diff --check
```

技能变更还需运行仓库的技能调用元数据校验。需要逐行对齐的双语文档应比较中英文实际行数。最后重读一遍差异检查事实是否完整，再读一遍检查简洁性、导航和责任归属。
