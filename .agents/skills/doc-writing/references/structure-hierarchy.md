# 页面结构与层级

## Summary

每个页面先给新人一个简短的入口，再展开操作或实现深度。跨模块的学习和工程材料放在有明确意图的 `docs/` 层级下，模块说明则留在模块代码旁边。小型规则文件各自负责一条可独立搜索的要求，但任意碎片化并不是目标。最后的 Dev Note 把活跃的工作语境与上方稳定的解释隔离开。

## 页面顺序

在格式归属方允许时，由人编写的面向人页面使用以下顺序。固定章节名（`Summary`、`Table of Contents`、`Further Exploration`、`Dev Note`）保持英文，正文使用中文，以便跨页面检索和机械检查。生成产物可以生成同样的入口章节，而 Agent Note 和复盘保留各自由仓库定义的骨架。

1. YAML 元数据。
2. H1 标题。
3. `## Summary`：三到五句解释性文字，说明读者能做什么或观察到什么、读者为什么关心、主要运行模型以及最重要的边界。模块文档的 Summary 还受 Summary 门禁的长度约束（见[模块文档评审](review.md#模块文档评审)）。
4. `## Table of Contents`：链接到页面的 H2 章节；保持导航性，不要写成描述。
5. 稳定内容，按从面向用户的使用到面向开发者的设计与操作细节排序。
6. 可选的 `## Further Exploration`，提供面向新人的相邻主题链接。
7. 最后的 `## Dev Note`，承载非权威的活跃工作语境。

不要给机器自有的小文件、生成片段或由已执行解析器定义其他头部的格式强行套上 Summary/Table of Contents 外壳。在格式归属方中说明例外，而不是产出无效输出。模块文档要求 `已知限制与暂缓工作` 作为最后一个内容 H2 章节：把 `Further Exploration` 放在它之前，并在该章节内以折叠的 `### Dev Note` 收尾。模块组文档没有使用方式、行为契约和限制章节，以 `Dev Note` 直接收尾。

## 章节推进

每个实质性 H2 都在表格、代码或 H3 子章节之前，先用一段简短的引导性文字开场。说明该章节的主题和与决策相关的要点；不要重复它的完整内容。

在页面内部，按读者深度排列内容：

1. 基础使用：何时选择该功能、必需输入、最短的安全示例、可观察的成功以及可能的恢复方式。
2. 进阶使用：配置选择、限制、操作和集成行为。
3. 开发者细节：归属、生命周期、数据模型、失败、性能、安全以及值得维护的扩展点。

把厚重的开发者细节和最后的 Dev Note 折叠进 `<details>` 块，同时保持章节标题可见（具体机制见 [style.md](style.md#可折叠的内容章节)）。

折叠的开发者细节按要求停留在概念层面：整体设计理念、主要组成部分的架构和粗线条的数据流——足以理解该模块如何工作——再加上源码导航表和指向代码的链接以提供精确细节。它绝不变成穷举目录：不出现完整 API 清单、字段清单、错误码枚举或 JSDoc 复述。

把穷举的生成类型、schema 或 catalog 放在一段紧凑的入口文字和稳定的索引之后。当一次查找就需要扫过无关分组时，按已有的领域归属方拆分。

## 文档层级

模块说明使用模块目录内的 README，并与源码放在一起。跨模块的 Markdown 按受众和学习意图组织，而不是把互不相关的页面平铺在 `docs/` 下。

```text
docs/
  learn/
    overview/
    practices/
  user/
  developer/
    discussion/
  scratch/
  subsystems/
```

把这当作目标地图，而不是可以借机大规模搬迁的许可。一次移动一个连贯主题，原子修复每个入站链接，并保持 `subsystems/` 扁平，因为其中的页面在逻辑上是平行的。

`docs/scratch/` 存放受版本跟踪、会过期的讨论，这些讨论必须能跨交接存活。每个 scratch 页面都写明归属方、创建日期、过期时间和晋升目标。本地的一次性笔记保持被忽略、不提交。

## 模块文档归属

模块文档放在模块代码目录内，与源码同级维护（`<module>/README.md`）。这样修改代码的人在同一个目录就能看到需要同步的说明书，评审也能把代码改动和文档改动放在一起看。

模块 README 只负责本模块的事实：能力、使用方式、行为契约、职责边界、内部设计和已知限制。跨模块的行为与契约属于上层系统文档，类型与语义属于所属子系统页面，决策理由属于 Agent Note，事件叙述属于复盘。模块文档不因模块形态改变类型；形态差异通过使用方式和行为契约表达，而不是通过另一套模板。

模块组文档（`<module-group>/README.md`）按需放在模块组目录，负责组定位、直接下属模块的职责、组合关系和导航。它只列直接下属模块，不递归展开；模块自己的能力、使用方式、契约和限制留在模块 README，组文档只做链接。模块组的目录层级由项目的模块组织决定，不要求每个父目录都有 README。

## 小型规则文件

当一条规则、实践、示例族或决策拥有自己的归属方、变更节奏、入站链接或校验时，给它一个单独的小文件。把相关文件归入描述性的层级，例如 `docs/developer/code-quality/`。如果拆分会导致读者为了理解一项义务而打开多个文件，就把紧密耦合的规则放在一起。

索引页面用三到五句话说明该文件夹，并按用途链接其直接子项。它不复述每个子项的规则。

## Further Exploration

这个可选章节面向读完页面、想获得相邻理解的新人。链接三到七个直接相关的页面，按从最近的前置条件到更深入的探索排序，并用短语说明每个页面补充了什么。不要把它变成完整的站点索引。

## Dev Note 归属

由人编写的页面以 Dev Note 收尾，但要明确它非权威。活跃假设、兼容性顾虑、粗略的替代方案、进度指引和未决问题可以放在这里；稳定的行为、必需的限制和已接受的决策理由属于它们各自的常规归属方。

Dev Note 可以镜像或链接任务进度，但不得变成第二个可写的任务队列。工作收尾时，把持久结论晋升出去，把可复用的理由移到 Agent Note，把事件时间线留在复盘中，并删除已解决的讨论。Git 历史会保留旧迭代。

## Dev Note

强制的最后章节刻意是由人编写页面中最不打磨的部分，但它仍然有生命周期纪律。空的 Dev Note 应写 `None.`，而不是堆叠占位文字；生成的和由解析器自有的格式可以通过具名例外省略它。
