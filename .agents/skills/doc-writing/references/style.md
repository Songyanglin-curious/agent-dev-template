# 页面风格

## 摘要

页面级风格偏好在以下几方面让页面便于扫读、不易误读：简短的 摘要、按读者深度安排的章节内容、受控的页面文字、主要部分之间的 `-----` 分隔线、保持章节标题可见的 `<details>` 折叠，以及有节制的强调。句子层面的编辑判断、术语核对和覆盖范围由 [prose-standard](../../prose-standard/SKILL.md) 负责，本参考只规定页面层面的格式和章节内容规则。

## 简短的摘要

每个由人编写的页面都以简短的 `摘要` 开头：一段三到五句话的文字，说明读者能做什么或观察到什么、读者为什么关心、运行模型以及最重要的边界。

摘要 和面向用户的章节描述对象能做什么——结果、收益、何时选择它、主要代价——而不是它的角色、类型或内部身份。“该模块导出一个 `Writer` 类并在内部维护队列”是在讲身份；“写入一条记录后重启进程，记录仍然存在”才是在讲它能做什么。除非读者会直接在配置、命令或公共 API 中使用，否则省略源码标识符。

目录和各章节承载细节；位置和章节顺序见 [structure-hierarchy.md](structure-hierarchy.md#页面顺序)。英文模块文档的摘要还受摘要门禁的长度约束，限制数值和中文计数口径见[模块文档评审](review.md#模块文档评审)。

## 页面文字要求

完整命题规则——保留执行者、条件、时序、情态、例外与否定的保证——由 [prose-standard](../../prose-standard/SKILL.md) 负责。页面文字在此基础上还要满足三条，它们是评审提示，不是机械门禁：

- 每个概念只用一个固定术语，全文不为了变化而轮换同义词；同一概念在不同页面沿用同一名称。
- 每个句子只放一个主要动作。出现三个或更多步骤或条件时改用列表。
- 保持情态、时序、例外和数字不变，不为了缩短句子而删除或加强它们。

精确性会下降时保留更长的句子。长度只是评审提示；绝不要为了满足长度目标而删除或加强 `must`、`may`、`never`、时序、例外、数字或其他约定用语。

## 章节内容规则

这些规则决定一个章节可以说什么。它们适用于每个由人编写的面向人页面，对模块文档尤其严格。

- **开发者章节讲解释，不做罗列。** 折叠的内部设计涵盖整体设计理念、主要组成部分和粗线条的数据流——足以理解模块如何工作——并链接源码以提供精确细节。折叠区里不出现完整的 API 目录、穷举的字段清单、错误码枚举或 JSDoc 复述。
- **开发备注是唯一允许粗糙的区域。** 半成品想法、草稿、未定方向、实测产物和工作假设只放在最后的开发备注中，并明确标注为非权威内容。其他每个章节都是打磨过的、描述当前状态的文字。
- **读者可见的效果优先。** 模块改变模型可见的输入、工具、输出或错误时，在行为契约中写明这些可见效果及其归属方，而不是把另一处的措辞抄过来。

## 章节分隔线

用单独一行的 `-----` 水平分隔线隔开页面的主要部分，并在前后各留一个空行。紧跟在段落之后的水平线会被解析成 Setext 标题。模板分隔的是：元数据 → 使用章节 → 折叠的开发者章节 → 延伸阅读。

## 可折叠的内容章节

把面向开发者的细节和最后的开发备注折叠进 GitHub 原生的 `<details>`/`<summary>` 块。保持章节标题（H2 或 H3）及其锚点可见；只折叠标题下的内容。块内部在 `<summary>` 之后留一个空行，所有 Markdown 行都保持在第 0 列（缩进的内容会变成代码块），并在空行之后以 `</details>` 结束。折叠区内的标题、列表、表格和链接会正常解析，并保留各自的锚点。

模块文档中，`已知限制与暂缓工作` 是最后一个 H2 内容章节，`开发备注` 作为该章节下带锚点的折叠 H3。其他 kind 的折叠位置见各自模板。

## 强调的使用

粗体只留给改变行为的从句或真正重要的对比。在对比表中，只把列标题和每行的关键值加粗。
