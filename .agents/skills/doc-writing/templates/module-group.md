# 模板：module-group

用于描述一组相关模块的模块组文档。模块组文档是导航与分工地图：说明这组模块整体提供什么能力、由哪些直接下属模块组成、它们如何组合，以及读者应该去哪份模块文档看细节。它不描述单个模块的使用方式、行为契约或内部设计，也不重复模块自己负责的事实。

模块组按需使用：不要求每个项目建立模块分组，也不要求每个父级目录都有 README；模块组不要求自身具有独立的软件入口或交互契约。只有当一组模块需要被一起理解，且它们的分工或组合关系会影响读者选择或修改时，才建立模块组文档。模块组目录的具体位置由项目的模块组织决定，不绑定 `packages/`、`src/` 等固定目录。

## 元数据

```yaml
---
description: "该模块组覆盖的能力族、组内模块的分工，以及读者应在何时打开这份导航文档。"
kind: "module-group"
---
```

## 骨架

```markdown
# <组名>

## 摘要

三到五句话：该组提供什么能力、读者能用它完成什么、组内模块如何分工，以及最重要的边界。

## 目录

- [模块组定位](#模块组定位)
- [模块与职责](#模块与职责)
- [组合关系](#组合关系)
- [职责边界](#职责边界)
- [相关文档](#相关文档)
- [开发备注](#开发备注)

-----

## 模块组定位

一段引导文字：该组面向什么场景，读者何时应当使用这组模块，以及与相邻组或替代方案的分界。

## 模块与职责

一段引导文字：本组由哪些直接下属模块或子模块组组成，读者按什么顺序阅读。

| 模块或子模块组 | 职责 |
|---|---|
| [`<module>`](<module>/README.md) | 一句话职责：该模块为这组能力贡献什么 |

## 组合关系

一段引导文字：模块之间如何协作、依赖方向、典型组合顺序，以及这些关系如何影响选择、配置或修改。

## 职责边界

- 本组负责：组内模块的共同约定、组合方式和整体能力。
- 本组不负责：单个模块的使用方式、行为契约、配置和限制（链接到对应的模块文档）；跨组的行为与规则（链接到对应归属方）。

## 相关文档

- [相邻归属方](<path>) — 它补充了什么。

## 开发备注

None.
```

## 规则

- **先核对模块清单。** 动笔前确认直接下属模块的边界与文档位置，模块表每一行都必须指向真实存在的模块文档；模块被移动、拆分或合并时，在同一次变更中更新本表。
- **只列直接下属模块或子模块组。** 一行一个成员，职责文字说明它为本组贡献什么，不写内部实现、配置项或行为细节；更深的层级链接到子组文档，不要在一次表里递归展开。只有当模块形态、入口类型或所属层次的差异能帮助读者在直接模块之间做选择时，才给模块表增加列。
- **模块文档归模块自己。** 能力细节、使用方式、行为契约、配置、限制和内部设计留在 `<module>/README.md`；本模板不设置这些章节，也不复制它们的内容。需要读者知道的跨模块约定写在「组合关系」里并链接归属方。
- **组合关系要能指导选择。** 说明依赖方向、协作顺序和失败时的连带影响，而不是罗列调用细节；如果两个模块不可互换，写清选择条件。
- **模块组没有运行时行为，也不要求有独立入口。** 不写安装步骤、最小示例或性能数字；这些属于模块文档。组如果有跨模块的启动顺序或共同配置，写在组合关系中并链接权威归属方。
- **摘要说明这组能力能做什么。** 不写它在仓库结构中的位置或内部命名；组名与目录由项目组织决定，frontmatter 不重复。
- **导航链接必须有效。** 模块表、相关文档和开发备注中的链接都要能解析；改写组名或移动目录时原子修复所有入站链接。
- **摘要受门禁约束。** 模块组摘要与模块摘要采用同一长度上限，由 `verify-module-readmes` 校验。
