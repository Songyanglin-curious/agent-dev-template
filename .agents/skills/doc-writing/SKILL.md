# 项目文档编写

## Summary

本规范让每个页面都可被搜索、可被新人读懂，并且对 agent 和维护者足够精确。先遵循仓库的 `AGENTS.md` 与已执行的校验门禁，再用本流程处理按 kind 映射的元数据、渐进式细节、语料审计和事实核验。坚持“一个事实一个归属方”：源码、测试、配置、生成目录、模块文档、系统文档、Agent Note 和复盘各自保留自己那一类事实，其他位置只做引用。模块文档（Module README）随模块代码维护，是读者认识模块能力、使用方式和边界的入口；模块组文档（Module Group README）按需放在模块组目录，负责分工与导航。

## 核心原则

- **一个事实一个归属方。** 每项事实只写在承担该职责的位置，其他文档链接过去。层级划分见 [docs/AGENTS.md](../../../docs/AGENTS.md) 的分类法。
- **重要声明有证据。** 行为、命令、默认值、限制和失败来自代码、测试、配置或实际执行结果；没有证据的声明不写入。
- **普通文档描述当前实现，研发记录保存历史。** 系统文档与模块文档只讲现在能观察到的行为；决策依据、被否决的方案和历史演进留在 Agent Note、复盘和持久化记录中。
- **渐进式细节。** 页面先给系统全貌和常见路径，再逐层深入到模块、接口和实现；穷举事实始终只隔一个直接链接或一层折叠。
- **简洁但不删约束。** 常见路径只保留达成其结果所需的事实；失败情形、归属关系、限制条件和其他必需约定不因精简而删除。

## 工作流程

对每个请求范围都按以下顺序执行。

1. 阅读根目录及更具体层级的 `AGENTS.md`、[文档标准](../../../docs/AGENTS.md)、目标页面及其源码/测试、导航归属方。
2. 按主要职责和读者为页面分类：产品快速上手、用户任务指南、贡献者教程、架构概览、模块/模块组/子系统参考、生成式参考、agent 指令、决策记录或 scratch。
3. 把页面放到最近的归属方。模块文档放在模块代码旁边；跨模块的学习、用户、开发者、架构、讨论和会过期的 scratch 材料放在 `docs/`。
4. 在写细节之前，先确定读者的起始状态、可观察结果、可能的失败、恢复路径以及下一个有用的深度层级。
5. 添加或修订 YAML 元数据——为本文档的职责指定与模板对应的 `kind`——然后按顺序写 `Summary`、`Table of Contents`、面向用户的内容、面向开发者的内容、可选的 `Further Exploration` 和最后的 `Dev Note`。
6. 按下面的事实核验流程核验每一项声明，先更新归属方，再更新衍生产物。
7. 在同一次变更中更新引用本文档的位置：索引页、同目录 README、生成区域和入站链接。移动或重命名时原子完成。
8. 先跑针对性检查，再跑完整文档门禁（见[验证](references/review.md#验证)）；重读完整 diff，先看正确性，再看简洁性和与仓库的契合度。

## 事实核验流程

文档描述的是软件当前的行为，而操作类声明的唯一有效证据是实际执行过。每个新文档，以及每个包含操作、命令、默认值、错误或平台差异声明的新段落，都必须执行本流程。

1. **写接入指引前先判定模块形态。** 读事实，不要读目录名：从模块 manifest、入口文件和配置声明判断它是常驻服务、进程内库、插件、命令行工具还是一次性脚本。有安装机制的模块写经过验证的安装路径；没有安装机制的模块只写实际的调用或加载方式，绝不套用不存在的安装指引，也不把可执行形态的启动方式写成库用法。写模块组文档前先核对直接下属模块的清单与文档位置，模块表每一行都必须指向真实存在的模块文档。
2. **针对当前 checkout 执行每一项声明的操作。** 按文档将要展示的样子，逐条执行每个命令、配置片段和示例；只写观察到的内容，包括确切输出、警告和失败模式。如果某项声明依赖你没有的凭据或网络，说明这一点并写出核验归属方，而不要断言该行为。
3. **删掉无法复现的内容。** 绝不凭记忆、类比或相邻模块的 README 搬运命令、字段、默认值或行为。声明无法复现时，修声明，不要修测试。
4. **用最新代码检查旧文档。** 修订既有页面前先执行 `git fetch`，把相关章节与默认分支的最新提交比对；Git 历史可恢复旧文本。上游过时的说法仍然是错的：对照代码改正，而不是对照旧文案。
5. **在同一次变更内同步归属方与衍生产物。** 更新源码、测试、配置、生成目录、索引和入站链接，重新生成受影响的产物；不要手工编辑生成区域。

## 文档类型与模板

`kind` frontmatter 字段只选择一个模板。[元数据与链接](references/metadata-and-links.md#kind-体系)中的每个 kind 恰好对应 [`templates/`](templates/) 里的一个模板文件，每个模板也只支撑一个 kind。

- `module` → [templates/module.md](templates/module.md)：随模块代码维护的模块文档——能力说明、使用方式、行为契约、职责边界、折叠的内部设计、已知限制与源码导航。
- `module-group` → [templates/module-group.md](templates/module-group.md)：模块组文档——组定位、直接下属模块的职责、组合关系与导航链接；按需使用，不重复模块自己负责的契约。
- `persistence-change` → [templates/persistence-change.md](templates/persistence-change.md)：`docs/persistence-changes/` 下带日期的记录——确认机械检测到的持久化数据结构变更，附各 root 的前驱记录和生成的 after schema。
- `persistence-release` → [templates/persistence-release.md](templates/persistence-release.md)：`docs/persistence-changes/releases/` 下按发布标签固定的记录——比较重建出的历史类型，但不声称已做兼容性确认。
- `persistence-format` → [templates/persistence-format.md](templates/persistence-format.md)：`docs/persistence-changes/historical-formats/` 下的历史持久化格式检查点，附完整 schema；当前写入器使用现有的 catalog。

动笔前先打开模板，遵循其骨架和规则；模板会说明该 kind 是什么、页面如何组织，以及每一节需要承担哪些事实核验。只有同时具备独立模板文件、已记录的仓库位置或已声明的归属方，以及能把文档映射到该 kind 的针对性检查时，才新增 kind。当前文档类型分两组：模块类（`module`、`module-group`）和持久化记录类。模块组按需使用，没有模块分组时不必创建；后续扩展文档类型时按同样的三项条件补齐，只增加名称不算新增 kind。

持久化记录的检测、生成和校验方式由具体项目的持久化技术决定——关系数据库、配置文件、游戏存档、事件日志、导入导出文件等各有不同的提取方式，本 skill 只规定记录结构、声明语义和核验要求。本模板项目自身没有需要长期兼容的业务数据格式，因此当前只保留三类记录模板及其规范，不实现自动化；使用模板的项目引入真实持久化数据时，按所用技术实现提取器、校验器和生成区域。不要把某一种技术栈（例如 TypeScript 的 JSONL 会话文件）的实现当成通用前提。

## 质量标准

评审时使用以下定义。

- **简短：** 常见路径只包含达成其结果所需的事实；穷举性的真相始终只隔一个直接链接或一层细节。
- **直观：** 前置条件出现在依赖概念之前，下一个动作显而易见，标题使用读者会搜索的术语。
- **友好：** 读者能识别成功、在行动前理解风险、从可能的失败中恢复，并选择是否继续深入。
- **准确：** 每一项持久声明都有唯一归属方，以及与风险相称的核验路径。
- **agent 可读：** 元数据、稳定标题、锚点、术语、归属关系以及当前/拟定状态，支持在不加载整个语料库的情况下做定向检索。
- **新人可完整理解：** 不具备仓库背景的专业工程师，能通过三到五个互链页面重建相关架构或功能。

## 语料审计与字数预算

审计按[评审标准](references/review.md#语料审计)执行：阅读归属约定文件本身，用 grep 排查重复规则，把手工目录和状态清单换成权威归属方，删除过时内容和失效链接。

字数预算按[评审标准](references/review.md#字数预算)执行：常驻文档受 `scripts/doc-budgets.manifest.json` 中的上限约束，`pnpm run verify-doc-budgets` 按 CJK 字符与空白分词的混合口径校验；超限时先迁移、再压缩，最后才上调，达标时至少保留 5% 余量。

## 验证

验证的是受影响的格式，而不仅仅是 Markdown 语法。先跑 `pnpm run test:docs` 和最小针对性检查；按项目实现的门禁单独说明。检查项与命令见[评审标准](references/review.md#验证)。
