# 研发流程

## Summary

本流程把文档工作嵌入研发活动，而不是留到结束之后。每个步骤都指向已有的归属方：输入在 `研发输入/`，决策在 `.agents/notes/`，当前系统在 `docs/`，工程知识在准则、模式、cookbook 和 Skills 中。流程只规定顺序与判断点，不复制那些文档的内容。

## 何时使用

除机械性修改外，以下任务进入本流程：新增或改变可观察行为、修复有系统原因的缺陷、调整模块边界或依赖、修改文档体系或门禁、变更持久化格式、引入或修改 Skill。机械性修改包括拼写修正、格式化、重命名局部变量和纯文案调整；这类修改仍需运行门禁，但不需要立提案或写复盘。

## 流程

### 1. 明确问题与验收

从用户请求、缺陷报告或 [研发输入](../../../研发输入/README.md) 中写出要解决的问题和可观察的完成条件。信息不足时先调查或询问，不用假设填补。问题的最终归属是 Agent Note 的 `## Problem` 或一次任务的交付说明，不是散落的对话。

### 2. 定位影响面

按 [架构](../../../docs/architecture.md) → [子系统](../../../docs/subsystems/README.md) → 模块文档的顺序阅读受影响能力，再打开对应源码和测试。记录三类候选归属方：拥有该行为的系统文档、拥有该取舍的 Agent Note、拥有该工件检查的防御性模式。不要从目录名猜模块边界。

### 3. 决定是否建立提案

只有满足至少一项时，在 `.agents/notes/proposed/` 建立记录：取舍需要长期保留、存在值得记住的被否决方案、影响跨模块契约、不可逆或涉及持久化与安全。局部实现选择留在代码注释或任务说明里。已经做出的重大决策直接在 `implemented/` 建立，并链接取代关系。

建立前先按 [archive-agent-notes](../archive-agent-notes/SKILL.md) 检查是否已有记录拥有同一决策；已有则更新它，不为同一决策建第二份。

### 4. 实施

修改代码、测试、配置和文档。遵守 [core-guidelines](../../../docs/core-guidelines/README.md) 的设计规则；修改并发、生命周期、协议、持久化或错误处理前，先读对应 [防御性模式](../../../docs/defensive-patterns/README.md)。保持变更范围与问题一致，不顺手做无关重构。

### 5. 同步归属文档

运行 `pnpm run verify-change-docs`，按输出的每个归属方逐项核对；本地默认提示，CI 的 `--strict` 只执行已经建立的 `require` 规则。再对照根 [AGENTS.md](../../../AGENTS.md) 的触发表检查是否遗漏。系统文档描述当前状态，implemented Agent Note 描述已交付的现实；被取代的记录按规则归档或合并。改变类型、接口或持久化结构时，同一次变更更新所属子系统页、模块文档或持久化记录。

### 6. 沉淀工程知识

只在经验可复用时沉淀：隐蔽且系统性的故障写 [复盘](../../../docs/postmortem/README.md)，并至少产出一条防御性模式；反复出现的正确或错误写法写入 [核心准则](../../../docs/core-guidelines/README.md) 或 [防御性模式](../../../docs/defensive-patterns/README.md)；已验证的固定步骤写入 [cookbook](../../../docs/cookbook/README.md)；需要在特定场景加载的判断标准写入 Skill。一次性结论留在 Agent Note，不新建知识层。

### 7. 验证

运行与改动范围相称的检查：项目自身的测试与构建，加上 `pnpm run test:gates`、`pnpm run test:docs` 和 `pnpm run test:notes`。修改门禁时 `test:gates` 必须通过。保留实际输出；失败时修复原因，不跳过、不修饰测试。

### 8. 交付报告

交付说明列出：改动内容、同步了哪些文档、变更影响清单的结果、实际执行的验证命令与结果、未覆盖或尚未解决的问题。没有执行的检查不写成通过；无法验证的声明标注为未验证并说明原因。

## 判断标准

- **需要 Agent Note**：未来读者会问“为什么不是另一种做法”；或者决定约束了后续多个模块；或者否决了一个看起来合理但代价更高的方案。
- **不需要 Agent Note**：实现细节、局部优化、跟随既有模式的改动、单纯的缺陷修复（除非复盘揭示了系统性缺口）。
- **需要复盘**：故障隐蔽、暴露系统性缺口、重复发现成本高，三者同时成立。
- **需要新 Skill**：存在明确的触发场景、需要多步判断，并且规则不适合放进常驻 `AGENTS.md`。
- **需要新门禁**：约束可机械判定、反复出现，且已有唯一归属文档。

## 反模式

- 代码先合并，文档留到“以后补”。以后不会到来，且变更上下文已经丢失。
- 为每个任务写 Agent Note，把决策语料变成工作日志。
- 在 implemented 记录里保留计划、迁移步骤或验收清单。
- 运行门禁后不读变更影响清单，把“退出 0”当成“文档已同步”。
- 把可复用经验留在对话或提交信息里，不写进任何归属方。
- 为了通过检查而扩大豁免、删除规则或制造空文档。
