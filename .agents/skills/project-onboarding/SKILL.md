# 项目初始化与接入

## 原则

- **空项目自然生长**：从目标、约束和最小架构开始，随代码出现再增加模块和子系统。
- **已有项目代码优先**：以入口、构建、测试、配置和实际行为为主要依据，旧文档只作参考。
- **宜少不宜多**：只记录有独立认知价值或独立维护价值的单元。
- **人最终确认**：Agent 调查并提出有证据的建议，不自行认定架构、模块和子系统边界。
- **不做批量生成**：不按目录名给每个文件夹写 README；没有证据的声明不写入。

## 空项目

1. 记录项目目标、用户、外部约束和验收方式；原始材料放 `研发输入/`，不写成已确认决策。
2. 建立最小 `README.md`、根 `AGENTS.md` 和 `docs/architecture.md`；小项目允许架构只有一页。
3. 只建立当前已经存在的模块文档；没有代码的层级不建空目录。
4. 建立最小的本地检查入口（如 `test:docs`、`test:notes`），随项目技术栈再增加代码检查和 CI。
5. 出现长期取舍时按 [Agent Note 规则](../../notes/README.md) 建 Note；机械或局部修改不建。

## 已有项目

### 1. 完整备份与隔离

- 完整备份旧文档、旧 `AGENTS.md`、开发 README、索引、AI 中间过程和旧流程材料，保留原路径与版本；备份是证据，不是新体系的一部分。
- 把备份放到新体系不会自动加载的位置：仓库外，或仓库内明确隔离的只读目录。隔离区不要求遵守新体系的目录、链接或 AGENTS 规则。
- **默认移走旧治理入口**：旧 `AGENTS.md`、开发 README、贡献指南、旧索引、旧流程/模板/检查说明和 AI 中间过程移入隔离区，不再保留在活动树中；不要只贴“非当前权威”标签而继续让它们参与导航。
- **根 `README.md` 默认保留**：它是项目的稳定入口，不随旧体系一起移动；在新体系中改写为入口页，链接新的 `AGENTS.md`、architecture 和常用命令，移除旧流程段落，避免双重权威。
- 根 README 只有在“仅是旧研发入口、没有产品/使用价值”时，才在新 README 建立后移入隔离区；不要为了形式统一而移动仍承担安装、使用或 API 说明的 README。
- 产品 README、API/安装/使用说明、法律文件、仍描述当前代码事实的模块文档、原始输入和仍在使用的构建/CI 配置不属于旧治理文档，不盲目移动；旧“开发 README”与产品 README 先分类。
- 移动前先建立新入口，并保留“旧路径 → 新归属或隔离位置”的映射，避免外部链接和团队书签直接失效。

### 2. 筛选旧资料

旧资料不是全部迁移，也不是全部长期保留。按“是否影响当前维护”分流：

| 旧资料类型 | 判断 | 处理 |
|---|---|---|
| 当前项目事实（入口、架构、配置、契约、限制） | 能用代码、测试、配置或实际行为验证 | 以代码为准重建到 `docs/`、模块 README 或子系统页；旧文只作线索并保留来源链接 |
| 真实需求、外部约束、参考资料 | 有来源、仍适用于当前项目 | 保留在 `研发输入/`，用链接关联任务或 Agent Note；不复制进系统文档 |
| 仍指导未来的设计理由、替代方案、被否决方案 | 有长期决策价值 | 建立或更新 Agent Note，链接原始资料；不把旧结论直接当当前事实 |
| 历史记录、已完成方案、低价值资料 | 不影响当前维护，但可能有历史价值 | 留在隔离区，不迁移；由人决定保留或清理 |
| 旧 AGENTS、开发 README、索引、旧流程和管理规则 | 属于旧体系的治理入口 | 默认移入隔离区，不进入新入口；根 README 保留并改写为新入口；产品/API/模块文档按当前事实保留或更新 |
| AI 中间过程、重复总结、草稿、过时清单 | 没有独立价值 | 不迁移；随隔离区由人清理 |
| 无法确认的事实 | 证据不足 | 记录为未知或缺口，不写成当前事实 |

筛选时遵守“一个事实一个归属”：旧文只提供来源和线索，当前事实由代码和测试重建，理由进 Agent Note，原始要求留在 `研发输入/`。不要为了“保留全部历史”而复制整棵旧文档树。

### 3. 建立代码事实

至少调查：

| 事实 | 证据 |
|---|---|
| 入口与运行方式 | manifest、入口文件、启动脚本、部署配置 |
| 构建与测试 | 构建文件、测试目录、实际可执行命令 |
| 配置与外部依赖 | 配置文件、环境变量、数据库/消息/外部 API |
| 数据与兼容 | schema、迁移、持久化格式、版本策略 |
| 主要单元 | 源码目录、调用关系、职责边界、独立发布/维护方式 |

不要从目录名推断模块边界。记录每条建议的文件、测试或配置证据。

### 4. 提出候选结构

列候选单元，并说明证据：

| 候选 | 职责 | 证据 | 建议 |
|---|---|---|---|
| 模块/服务/组件 | 提供什么、谁使用 | 入口、源码、测试、配置 | module / subsystem / 暂不建 |

判断标准：

- **Module**：具有独立职责和维护价值的软件单元；代码目录、入口和部署形态不是固定条件，具体形态由模块文档说明。判断时看是否有明确接口或使用方式、自己的配置/生命周期，或独立理解和维护价值；不是每个文件夹、Controller、Service 都是 Module。
- **Subsystem**：有独立认知价值，并且存在跨单元契约、复杂行为或生命周期。两个模块的简单调用不建子系统。
- **Module Group**：只在多个模块需要一起理解、导航成本明显时建立。
- **Architecture**：所有项目都需要最小版本；小项目可以只有一页，不强行写长文。

### 5. 人确认边界

把候选结构、证据和不确定项交给维护者确认。确认前不创建永久目录、不批量改写旧文档、不删除隔离区资料。确认后再建立最小 Architecture、必要的 Module README 和子系统页。

### 6. 新体系接管与旧资料退出

- 新体系只记录当前事实、原始输入和长期决策；旧文档保持只读参考，不进入新入口导航，也不从旧索引自动加载。
- 为当前仍有效的关键决策建立初始 Agent Note，并链接原始输入和历史依据。
- 明确旧资料的退出条件：当前事实已由代码和测试重建、没有活跃文档引用、没有待确认的迁移项，并由维护者确认可以清理。
- 仍被引用的资料不静默删除；已失效但可能有历史价值的资料留在隔离区，由人决定保留或清理，不自动删除。
- 运行现有门禁，记录未覆盖项；不要用空目录、空规则或占位文字补齐结构。

## 输出

报告应包含：调查范围、关键证据、旧资料筛选结果（迁移、隔离、保留的根 README、待确认）、旧路径到新归属的映射、候选结构、人工确认结果、已建立的文档、未确认或暂缓的边界，以及实际运行的检查。不要声称未调查的模块已被理解，也不要把“旧资料已备份”写成“旧资料已迁移”。
